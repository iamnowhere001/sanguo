## 0. 三条使用规则

1. **「代码现状」列必须指向源码路径，不许指向另一份文档。** 这是上一轮病灶的根治办法 ——
   旧文档停在了 10-30，而代码继续跑，于是出现「文档说没做、代码做了」。
2. **「目标态」是裁决，不是已完成。** 未落地的一律写「待施工」，禁止用目标态冒充现状；
   反过来也不许把已实现的写成「未做」。
3. **数字只写一处。** 本文不写「59 城」「47 关防」「579 项」这类数字，引用 [项目基线](../00-基线/项目基线.md) §2。
4. **「三11 原义」列只做了关键词级外部检索，未逐条核验原作规则**，标 `（未核验）`；
   写入实现规格前须人工确认。本作事实一律标 `【代码】` + 路径。

## 5. 维护规则

1. 改了玩法代码 → 同一提交回填本矩阵「代码现状」列；改了裁决 → 同一次提交改 [设计总纲](设计总纲.md) §1 / §5 与本文 §1。
2. 新机制先在本矩阵占一行并写「待施工」，才允许进 [路线图](../04-计划/路线图.md)；没有行的提案视同讨论稿。
3. 与本文冲突的旧文档，按 [docs/README](../README.md) §4 处理：能定点改的改，被取代的进 archive 并写明被谁取代。
4. **待补门禁**：`npm run spec:check` —— 校验「代码现状」列引用的源码路径存在，
   并扫描 docs 里「现状：无 / 已实现 / 已裁决 / 待裁决」断言与代码标记对照，把语义漂移变成红灯；
   完成后并入 `npm run verify`，CI 接 `verify`（11-03 体检报告 §6 第 1 条）。
