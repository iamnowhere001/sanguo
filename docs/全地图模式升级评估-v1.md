# 全地图模式升级评估 v1

> 评估对象：《三国霸业》从「节点图 + 独立战棋场景」升级为《三国志11·威力加强版》式全地图模式。
> 基线：2026-10-26 工作区代码（`src` 24,898 行 / 92 文件，`tests` 6,174 行 / 38 文件 / 334 用例）。
> 性质：**只评估与方案设计，不含任何代码实现**。
> 结论口径：可行，但这不是"升级"，是**战略层换引擎**；建议按 M 档分五个阶段推进，不建议一步做到完整 L 档。

---

## 0. 结论先行

1. **技术可行性没有疑问**。栅格地图、A\* 寻路、分块渲染、地图编辑器都是成熟解法，没有任何一项需要自研不可替代的算法。
2. **真正的成本不在渲染，在状态拓扑**。当前"可达"由 `edges` 邻接表定义，全地图模式下由几何邻接定义。这一个变化会渗透到 AI、存档、UI、平衡的每一层。
3. **完整 L 档（地图即战场 + 设施 + 迷雾）约 150–220 人日**，对单人项目是 6–10 个月，期间零内容产出。**不建议**。
4. **M 档（地图上跑部队，战斗仍切场景）约 100–150 人日**，是体验/成本拐点。玩家感知到的"全地图感"九成来自"部队在地图上走"，而不是"战斗在哪个界面打"。
5. **有一个必须先解决的硬约束**：月回合 + 61 城 + 合理行军速度，三者不能同时成立。这是设计问题，不是实现问题，必须在阶段 0 裁决，否则后面全部返工。
6. **一处需要直说的风险**：全地图会稀释现有优势。本作现在的决策密度在"城内政令 + 一战一题 + 月报归因"，全地图模式的决策密度会转移到"部队调度与补给"。后者做不好，游戏会退化成走路模拟器——这是绝大多数三国志11 仿制品的死因。

**推荐路径**：S 档（1 个迭代，先换皮验证）→ M 档（4 个阶段，换骨架）→ L 档仅在 M 档验证通过后再议。

## 1. 基线：当前到底是什么

先纠正一个措辞。当前不是"分块地图"，是**抽象节点图**。这个区别决定了改造成本的方向。

| 维度 | 现状 | 代码位置 |
| --- | --- | --- |
| 地图结构 | 61 城节点 + 123 条带 cost 的边，无地块 | `src/data/tables/cities.ts`、`scenarios.ts` |
| 坐标语义 | `City.x/y` 是**示意坐标**（x 175–935 / y 120–675），只用于画布投影，不参与任何规则 | `City.x/y` |
| 地形 | 4 类（plain / mountain / forest / water），是**城池属性**，只决定战场模板与移动代价 | `unitClasses.ts` |
| 可达性 | `neighborsOf()` = 查邻接表；13 个源文件依赖 | `core/state.ts` |
| 出征 | 点击相邻敌城 → 立即生成 12×8 战场，无行军过程，无部队实体 | `battle/setup.ts` |
| 战斗 | 独立 `BattleState`，自带 grid / 单位 / 回合 / 30 天限时 / 随机流 | `systems/battle/*` 3,387 行 |
| 兵力归属 | 兵力挂在**武将**身上（`General.troops`），武将挂在**城**里（`locationId`，48 个文件涉及） | `core/state.ts` |
| 视野 | 无。全图所有城池的归属、兵力、资源对玩家完全可见 | `render/MapCanvas.tsx` |
| 渲染 | Canvas 2D，事件驱动重绘，无动画循环，无地形底图（纯程序化图形） | `MapCanvas.tsx` 724 行 |
| 存档 | 纯 JSON + `SAVE_VERSION = 3` + 迁移链，`structuredClone` 全量克隆 | `save/db.ts`、`core/reducer.ts` |

关键判断：**节点图比"分块地图"更容易改成连续地图**（没有块边界需要缝合），但**缺少地块数据基础**（没有地形栅格、没有通行性、没有距离度量）。所以工作量集中在"从零建立地块层"，而不是"改造现有地块"。

## 2. 目标：三国志11 式究竟是哪几件事

把目标形态拆开，才能判断哪些必须做、哪些可以砍。

| # | 特征 | 是否全地图模式的**必要条件** | 现有资产可复用度 |
| --- | --- | --- | --- |
| 1 | 一张连续地图承载所有实体（城市、部队、设施） | **是** | 低（需新建地块层） |
| 2 | 城市占据格子，控制周边领内 | **是** | 低 |
| 3 | 部队是地图实体，有行军、补给、ZOC | **是** | 低（现无部队实体） |
| 4 | 战斗发生在地图上，无场景切换 | 否 | 中（战斗逻辑可复用，坐标系要换） |
| 5 | 设施系统（农田/市场/箭楼）占格，产出与位置绑定 | 否 | 无 |
| 6 | 地形决定通行性、移动代价、战力修正 | **是** | 中（已有 6×5 地形修正表） |
| 7 | 情报与视野（敌领迷雾、侦察、伏兵） | 否 | 无 |

**这是本评估最重要的一张表**：特征 4、5、7 都是"可裁剪项"。砍掉它们，"全地图模式"仍然成立，成本却下降 40% 以上。

| 行军与寻路 | grid.ts 229（可复用思路） | **新增** | 全图 A\*、ZOC、路径预览、跨回合移动 | ~700 行 |
| 战斗接入 | setup 280 + resolve 504 | 改造 | 战场从地图裁切、遭遇触发、援军、撤退路径 | ~800 行 |
| 战斗内核 | combat/damage/tactics 612 | 扩展 | 伤害公式与计策逻辑可原样复用，仅作用域判定换坐标系 | ~250 行 |
| 战略 AI | aiStrategy 454 + ai 268 | 重写 | 城级决策 → 部队级调度（集结/行军/围城/避战） | ~1,300 行 |
| 城池/部队面板 | CityPanel 1,451 | 改造 | 出征对话框 → 编军对话框；城池面板加领内信息 | ~900 行 |
| 战斗 HUD | BattleScreen 1,199 | 扩展 | 保留场景时改动很小 | ~200 行 |
| 存档 | db 121 + migrate 121 | 改造 | 地图版本化、部队序列化、v3 迁移链 | ~400 行 |
| 内政/经济/外交/章节 | ~2,600 行 | 扩展 | 主要改"相邻"语义与调将（瞬时 → 行军） | ~400 行 |
| 测试 | 6,174 行 / 334 用例 | 重写 40% | 战斗与地图相关约 130 条要重写，内政/经济类基本不动 | ~2,500 行 |
| 平衡与沙盒 | scripts 5 个 | 扩展 | 新增"全图对局"沙盒（当前缺失） | ~400 行 |

**合计约 12,000–16,000 行新增/改动**，与现有 `src` 体量同级（24,898 行）。这就是"换引擎"的量化含义。

## 4. 三档方案对照

| 维度 | **S 档 · 地形化** | **M 档 · 部队上地图** | **L 档 · 完整三国志11** |
| --- | --- | --- | --- |
| 一张连续大地图 | ✅ 有地形、河流、山地 | ✅ | ✅ |
| 城市落位 | ✅ 按真实地理重标定 | ✅ | ✅ + footprint + 城门 |
| 部队在地图上移动 | ❌ 仍是"城→城"瞬时出征 | ✅ 逐格、跨回合 | ✅ |
| 战斗 | 仍切 12×8 场景 | 战场从大地图**裁切**生成 | 直接在地图上打 |
| 设施系统 | ❌ | ❌ | ✅ |
| 视野/迷雾 | ❌ | ❌ | ✅（可选） |
| 战略 AI 改动 | 只需适配新邻接 | 重写为部队调度 | 重写 + 战役 AI |
| 估算工作量 | **25–40 人日** | **100–150 人日** | **150–220 人日** |
| 复杂度等级 | 中高 | 高 | 极高 |
| 可回退性 | 高（纯表现层） | 中（状态模型变更） | 低 |
| 建议 | 先做，验证美术与手机端 | **推荐主线** | 暂缓 |

估算假设：单人 + AI 辅助，每日有效产出 150–200 行（含测试与调试），含 30% 返工余量。

## 5. 技术难点（按杀伤力排序）

### 难点 1 · 状态拓扑变更：从图到栅格（影响面最广）

`neighborsOf()` 现在是"查表"，全地图后是"查几何邻接"。听起来只是换个实现，实际影响 13 个源文件：

- `aiStrategy` 的攻击候选、窗口折扣、孤城判定全部基于邻接；
- `battle/setup` 的"目标必须相邻"校验；
- `domestic` 的调将合法性；
- `abandon` / `elimination` / `chapter` 的撤退与灭亡判定。

**风险**：这些逻辑是"图语义"的（离散、有限邻居），改成栅格后会变成"距离语义"（连续、半径、路径长度）。很多判定条件（如"孤城"、"多线受敌"）需要重新定义，不是改个函数调用就行。

**缓解**：保留一个**派生层** `adjacencyOf(state, cityId)`，内部用栅格距离 + 邻接城表计算，对外签名不变。这样 AI 与规则层可以先不动，只换实现。

### 难点 2 · `structuredClone` 全量克隆与大地图状态冲突（最隐蔽）

现有架构约定第 2 条：`reduce()` 先 `structuredClone` 整个 state，system 直接改草稿。当前 state 约 10–20KB，克隆成本可忽略。

加入地图后：

- 若地形存为 `Tile[]` 对象数组（5,000–7,000 个对象），每次点击克隆 5–15ms，**直接掉帧**；
- 若存为 `Uint8Array`（地形 1 字节/格），`structuredClone` 走 TypedArray 快路径，约 0.1–0.3ms，可接受。

**结论**：地形**必须**用 `TypedArray`，且作为不可变共享引用**不进 draft 克隆**。这需要打破现有"全量 clone"约定，改为"静态地图共享 + 动态状态克隆"。

**风险**：这是架构级改动，会牵动 `reducer`、`gameStore`、存档序列化三处。做晚了要返工。

### 难点 3 · 寻路规模与确定性（工程主线 C 的硬约束）

现有战棋寻路是 96 格 Dijkstra，每步重算，无压力。全地图后：

- 单次寻路 5,000–7,000 格，必须 A\*（启发式用切比雪夫或曼哈顿距离）；
- 每回合要算 30–80 支部队的路径，hard 难度下 AI 已实测 51.6ms，全图可能是 10–50 倍；
- **确定性要求**：A\* 的 tie-breaking 必须稳定（同代价节点按固定顺序出队），否则读档后路径不同，违反"读档 100% 复现"的工程主线。

**缓解**：A\* 的开放集用"代价 → 固定序坐标"的复合排序键；随机流新增 `march` 分流；寻路结果按回合缓存。

### 难点 4 · 节奏三角约束：月回合 / 61 城 / 行军速度（必须先裁决）

这是设计问题，但会决定所有实现参数。三种取值无法同时成立：

| 方案 | 地图尺度 | 步兵横穿全图 | 问题 |
| --- | --- | --- | --- |
| A. 月回合 + 大地图（96×72） | 每格 ~15km | 24–32 个月 | 太慢，玩家等不起 |
| B. 月回合 + 小地图（60×45） | 每格 ~25km | 12–15 个月 | 61 城太挤，平均 44 格/城 |
| C. **旬回合（3 回合/月）+ 中地图（84×64）** | 每格 ~18km | 6–9 个月 | 内政/经济/月报/章节全要适配 |

三国志11 的答案是 C。**建议选 C**，代价是约 15–25 人日的全局节奏适配，但这是让全地图模式"能玩"的必要投资。

若坚持月回合，建议同时把城数压到 35–40（内容损失），否则地图必然拥挤到失去空间感。

### 难点 5 · 战斗坐标系切换

`BattleState.grid` 现在是独立生成的 12×8 二维数组。全地图模式下有两种做法：

- **M 档**：战斗触发时从大地图**裁切**一块（如 20×14）作为战场，地形连续、城在战场内。改动集中在 `setup.ts`，`combat/tactics/ai` 基本不动。
- **L 档**：取消 `BattleState`，战斗直接读写地图状态。改动会扩散到全部 13 个 battle 文件，且"战场边界"变成动态概念（援军从哪个方向入场？溃散往哪跑？）。

**判断**：M 档的裁切方案能拿到 80% 的"全地图战斗"观感，成本只有 L 档的 35%。这也是推荐 M 档的核心理由。

### 难点 6 · 部队实体引入对武将位置语义的冲击

现在 `General.locationId` 是唯一位置真相，48 个文件引用。引入部队后会出现三种状态：驻城、在军、行军途中。所有 `locationId` 的判断都要回答"在军的武将算不算这城的守将"。

**风险点**：`defendersOf()`（守军）、`generalsOf()`（势力武将）、`garrisonCapOf()`（驻军上限）、撤退逻辑、俘虏逻辑全部依赖这个语义。改错一处就会出现"武将同时在城又在军"或"部队被打散后武将消失"。

**缓解**：拆成 `locationId`（城）+ `armyId`（军）两个字段，且约定互斥；`defendersOf()` 只返回 `armyId == null` 的武将；加一条不变量测试。

### 难点 7 · 战略 AI 从城级到部队级（最大风险，也是成败分水岭）

现有 `aiStrategy` 454 行，逻辑是"从哪座城打哪座城、带几个将、留多少守"。全地图后要回答的是：

- 几支部队？从哪些城集结？走哪条路？路上补给够不够？
- 遇到敌方野战部队，打还是绕？
- 围城时敌方援军来了，继续围还是撤？
- 多支部队如何协同（同一目标 / 分进合击 / 佯攻）？

这是三国志11 AI 的核心难点，也是"看起来像但不好玩"的分水岭。**AI 工作量通常是玩家侧的 3–5 倍**，因为要考虑所有部队的全局协同。

**缓解**：
1. 先做**脚本化 AI**（固定行为模板：集结 → 行军 → 围城 → 撤），能玩即可，不追求聪明；
2. 再做**评分式调度**（复用现有 `planAttackCandidates` 的评分思路，扩展到部队级）；
3. 保留 `aiEnabled` 开关与难度降级，保证 AI 出问题时游戏仍可玩。

### 难点 8 · 存档不兼容与地图版本化

节点图的拓扑与栅格地图无法互转（城市位置、距离、邻接全变了）。**旧存档必然作废**。

三种处理：
- **放弃**（推荐）：`SAVE_VERSION` 提到 4，旧档直接拒绝，提示"地图改版，请开新局"；
- **冻结**：旧档标记为 `classic-map` 只读，可查看不可续玩；
- **双轨**：保留节点图模式作为"经典地图"，与全地图并存——**不建议**，等于维护两套规则。

另外：地形数据应存在**配表**而非存档（静态 + 版本号引用），存档只存动态部分（城市归属、部队、设施、迷雾）。否则单个存档会膨胀到数百 KB，IndexedDB 写入变慢。

### 难点 9 · 渲染与手机端交互

现有 `MapCanvas` 是事件驱动重绘，无动画循环，画 61 个节点 + 123 条线。全地图后要画 5,000–7,000 个地形格 + 数十支部队 + 路径高亮，必须：

- 分层 canvas（地形层静态缓存 / 道路层 / 实体层 / UI 层），地形层用离屏 canvas 按缩放级别预渲染；
- 玩家视野裁剪（只画可见区块），避免每帧遍历全图；
- 拾取用"屏幕坐标 → 格坐标"反算，不能用 61 个点的距离遍历。

**手机端是硬约束**：现有方案是 2.1× 缩放 + 城池列表绕开点选精度。格网模式下，手指点 12px 的格子基本不可能。需要"格选 + 邻格吸附 + 部队列表双通道"，并且**必须在阶段 1 就做手机原型**，不能等到最后。

### 难点 10 · 视觉资产缺口（被低估）

现有美术是**纯程序化绘制**：黑底 + 网格 + 圆点 + 虚线，没有任何贴图。全地图模式下，5,000 个纯色格子会非常难看；地形要有可读性（山、河、湖、丘一眼能分），靠代码绘制山脉纹理的难度远高于画圆点。

两条路：
- 继续程序化（生成式地形纹理 + 等高线 + 河流曲线），需要较强的图形编程，约 8–12 人日；
- 引入美术资产（地形图块、山脉、河流），与项目现有"无素材"路线冲突，且要处理版权。

**建议**：先做程序化（用色阶 + 纹理噪点 + 符号叠加），验证观感后再决定是否引入资产。这条风险容易被"技术上可行"掩盖。

## 6. 复杂度评级

采用 5 级制（低 / 中 / 中高 / 高 / 极高）：

| 维度 | 等级 | 说明 |
| --- | --- | --- |
| 数据结构改造 | **高** | 拓扑变更 + TypedArray 约束 + 存档版本化 |
| 渲染与交互 | **高** | 分层缓存 + 手机端降级 + 拾取重写 |
| 规则与平衡 | **高** | 地形/补给/行军全要重新标定 |
| AI | **极高** | 城级 → 部队级，是公认的难点 |
| 工程量 | **高** | 12,000–16,000 行，与现有代码同量级 |
| 整体 | **高（架构级重构）** | 不是"加功能"，是"换战略层引擎" |

**一句话**：单个模块都有成熟解法，难的是它们必须同时成立，且互相约束（地图尺度 ↔ 回合粒度 ↔ AI 复杂度 ↔ 手机端可读性）。

## 7. 风险登记册

## 8. 分阶段升级方案

设计原则：**每个阶段结束都是一个可发布的可玩版本**，不是半成品。这是本作"垂直切片"哲学的延续，也是控制风险的核心手段。

### 阶段 0 · 规格裁决（3–5 人日，无玩法代码）

**目标**：把四个会决定所有实现参数的决策钉死，避免返工。

| 决策项 | 选项 | 建议 | 理由 |
| --- | --- | --- | --- |
| 回合粒度 | 月 / 旬 | **旬（3 回合/月）** | 唯一能同时满足"大地图 + 61 城 + 合理行军"的组合 |
| 网格类型 | 方形 4 邻 / 方形 8 邻 / 六边形 | **方形 4 邻** | 100% 复用现有曼哈顿距离与 ZOC 逻辑；手机点选更容易；视觉用底图弱化方格感 |
| 战斗形态 | 切场景 / 裁切战场 / 地图即战场 | **裁切战场** | 80% 观感，35% 成本 |
| 旧存档 | 放弃 / 冻结 / 双轨 | **放弃** | 垂直切片阶段无历史包袱 |

**产出**：`docs/全地图规格-v1.md`（坐标系、地图尺寸、地形枚举、行军公式、回合定义、存档版本策略）。

**准出门禁**：纸面推演能回答——"从许昌出兵到洛阳，几回合？粮耗多少？途中经过哪些地形？"答不上来不进阶段 1。

**依赖**：无。**回退点**：随时可停，零代码损失。

---

### 阶段 1 · 地图地基（25–35 人日）

**目标**：把"节点图画法"换成"地形图渲染"，但**玩法逻辑一行不改**。

关键改造点（按优先级）：

1. **地形栅格数据**：新增 `MapGrid`（`Uint8Array` 地形 + 通行性位图），作为静态配表。
2. **地图编辑器**（P0，不可省）：浏览器内的格网编辑器，能刷地形、放城、画河、导出 JSON。没有它，5,000 格无法维护。
3. **城市落位重标定**：61 城按真实地理重新落格，确定 footprint（1–4 格）。
4. **分层渲染**：地形层（离屏缓存）/ 道路层 / 实体层 / 交互层；相机与缩放沿用现有逻辑。
5. **拾取重写**：屏幕坐标 → 格坐标反算。
6. **手机端原型**：格选吸附 + 部队列表双通道。

**准出门禁**：
- 61 城在新地图上位置合理，无重叠、无落水；
- 桌面端拖动/缩放 60fps；手机端能准确选中目标城；
- 玩法与阶段 0 完全一致（节点图仍驱动一切）。

**依赖**：阶段 0。**回退点**：渲染层独立，回退只需切回旧 `MapCanvas`。

---

### 阶段 2 · 部队与行军（35–50 人日，风险最高）

**目标**：部队成为地图实体，能逐格移动、跨回合、遇敌停下。战斗仍走旧流程（到城触发）。

关键改造点：

1. **`Army` 实体**：`{ id, factionId, generalIds, troops, x, y, moveLeft, supply, morale, targetPath }`。
2. **武将位置语义拆分**：`locationId` + `armyId` 互斥；`defendersOf()` 加约束；补不变量测试。
3. **全图 A\***：代价来自地形 × 兵种表（复用 `MOVE_COST` 扩展为 8 地形）；结果按回合缓存。
4. **ZOC 与遭遇**：进入敌方 ZOC 停步；接触到敌部队/敌城触发遭遇事件。
5. **补给**：部队带粮，粮尽掉兵；补给线可选（先做"随身粮"，不做"粮道"，降低复杂度）。
6. **编辑交互**：编军对话框替代出征对话框；地图上路径预览与移动力高亮。
7. **AI 最小可用**：能把一支部队从 A 送到 B，不要求会野战。

**准出门禁**：
- 一支部队从许昌走到洛阳，路径可见、跨回合、遇敌停下；
- 读档后部队位置与路径完全复现（确定性）；
- 全图 AI 月结 ≤ 200ms（61 城 / 30 支部队规模）。

**依赖**：阶段 1。**回退点**：`Army` 可为空（无部队时退回瞬时出征），保证可降级。

**这是最危险的一阶段**：状态模型变了，48 个 `locationId` 引用全部要审。建议在此阶段冻结其他功能开发。

---

### 阶段 3 · 遭遇与战斗接入（20–30 人日）

**目标**：野战、攻城、撤退三条链路打通，战场从大地图裁切。

关键改造点：

1. **战场裁切**：以交战点为中心，从 `MapGrid` 裁一块 20×14 作为 `BattleState.grid`，地形连续、城在战场内。
2. **三类遭遇**：野战（部队 vs 部队）、攻城（部队 vs 城）、守城（城 vs 部队）。
3. **援军入场**：相邻格子的友军可加入，从战场边缘入场（M 档简化：只允许 1 支）。
4. **撤退路径**：败军沿地图退往最近友城，途中可被追击。
5. **时间对齐**：30 天限时改为"战斗天数 × 回合粒度"，与旬回合对齐。
6. **战报挂接**：保留现有月报/战报归因体系，把新战斗类型接进去。

**准出门禁**：
- 野战、攻城、守城、撤退四条链路各有端到端测试；
- 裁切战场的地形与大地图一致（同格同地形）；
- 战斗结果回写地图后，部队/城池状态一致（无幽灵部队、无重复武将）。

**依赖**：阶段 2 的 `Army` 与遭遇触发。**回退点**：裁切失败时退回固定模板（保留旧 `emptyGrid()` 作为兜底）。

---

### 阶段 4 · 战略 AI 与平衡（30–45 人日）

**目标**：AI 会集结、行军、围城、避战、撤退；游戏重新可玩。

关键改造点：

1. **AI 调度器**：替换 `planAttackCandidates` 的"城→城"模型，改为"军→目标"评分；保留原评分维度（兵力比、窗口折扣、城防、战利）。
2. **协同**：多支部队分进合击、佯攻、增援被围部队。
3. **避战与撤退**：兵力劣势时退回城内或绕行；补给不足时回撤。
4. **难度分层**：三档难度控制部队数、协同程度、窗口激进度。
5. **平衡重标定**：行军速度、粮耗、补给半径、攻城时间、部队编制上限。
6. **全图对局沙盒**（当前缺失）：自动化跑 N 局，输出胜率/平均统一时间/卡死检测。

**准出门禁**：
- 全图 AI 对局 20 局无卡死、无"部队原地打转"；
- 平均统一时间落在设计区间（建议 60–100 回合）；
- 三档难度胜率曲线单调（easy > normal > hard 的玩家胜率）；
- `npm run verify` 全绿（含新增不变量测试）。

**依赖**：阶段 3。**回退点**：AI 失败可降级为脚本化模板（阶段 2 的版本），游戏仍可玩。

---

### 阶段 5 · 可选延伸（L 档，40–70 人日，需重新评估）

只在阶段 4 验证通过后考虑：

- **战斗合一**：取消场景切换，战斗直接在地图进行（改全部 13 个 battle 文件）。
- **设施系统**：农田/市场/箭楼占格，产出与位置绑定（内容量最大）。
- **视野迷雾**：敌领不可见、侦察单位、伏兵。
- **关隘与港口**：特殊地形节点，控制通行。
- **水战**：河流/湖泊上的舰船单位与战斗规则。

**建议**：这五项里，**关隘/港口**性价比最高（成本低、空间感强），**设施系统**性价比最低（内容量大、与现有内政重复），**迷雾**与现有"信息前置"设计哲学冲突，需谨慎。

## 9. 阶段依赖与优先级

```
阶段0 规格裁决
   │
   ├─→ 阶段1 地图地基（可独立发布）
   │      │
   │      └─→ 阶段2 部队与行军（风险最高，冻结其他开发）
   │             │
   │             ├─→ 阶段3 遭遇与战斗（可与 4a 并行）
   │             │      │
   │             │      └─→ 阶段4 战略AI与平衡
   │             │             │
   │             │             └─→ 阶段5 可选延伸（L档）
   │             │
   │             └─→ 阶段2b 地图编辑器增强（可并行，非阻塞）
```

**MoSCoW 优先级**：

| 级别 | 内容 |
| --- | --- |
| **Must** | 地形栅格、城市落位、分层渲染、部队实体、A\* 行军、遭遇触发、AI 能出兵 |
| **Should** | 补给、ZOC、援军、路径预览、地形战力修正接入、手机端吸附 |
| **Could** | 设施、迷雾、关隘/港口、水战、粮道 |
| **Won't（本轮）** | 地图随机生成、多人、天气系统扩展、部队阵型 |

## 10. 需要拍板的五个问题

按影响面排序，建议在阶段 0 一次性定完：

1. **回合粒度改不改旬？** 不改，则地图尺度与城数必须二选一让步（建议减城到 35–40）。
2. **战斗切不切场景？** 切（M 档），还是保留（S 档）。这决定 100–150 人日 vs 25–40 人日。
3. **旧存档放弃吗？** 建议放弃，`SAVE_VERSION` 提到 4。
4. **美术走程序化还是引入资产？** 建议先程序化，阶段 1 看观感再定。
5. **现有四条现代机制（国策/事件/章节三幕/一战一题）保留吗？** 建议全保留——它们是本作与"普通三国志仿制品"的差异点，全地图化不应以牺牲它们为代价。

## 12. 一句话总结

技术上没有拦路虎，难的是**取舍**：全地图模式会拿走 6–10 个月，换一个"空间感"；而这个空间感有 80% 可以用 M 档拿到，剩下 20% 要再花一倍代价。先做 S 档验证观感，再走 M 档换骨架，L 档等 M 档跑通再谈——这是我对这个决策的建议。
