| 和游戏配表的关系 | 配置台以现有配表为**内置基线**；`npm run map:apply` 把文档回写成 `gates.ts` / `CITY_COORDS` |

### 0.1 先修正一处口径

`docs/02-系统/地图.md` 篇一 §2.1 写的是「12 关 + 16 渡 + 3 小路」，但当前 `GATES` 实表是：

| 类型 | 旧规格 | 当前实表 | 差异 |
| --- | ---: | ---: | --- |
| 关隘 `pass` | 12 | **13** | +1 |
| 渡口 `port` | 16 | **30** | +14（新增渭水、淮河、汉水、洞庭、鄱阳等渡口） |
| 小径 `trail` | 3 | **4** | +1 |

本文、配置台与数据清单一律以**代码实表**为准。30 处渡口里 26 处成对（13 对两岸渡口），不是重复计数；孟津 / 河阳、采石 / 横江、瓜洲 / 京口等仍是两岸各一处图标。

## 1. 坐标与栅格

### 1.1 世界坐标系

| 项 | 值 |
| --- | --- |
| 栅格 | 576 列 × 360 行 |
| 每格 | 12 世界单位 |
| 世界尺寸 | 6912 × 4320 |
| 原点 | 左上角 |
| 轴向 | `x` 向东，`y` 向南（屏幕坐标） |
| 精度 | 保留 1 位小数；拖拽吸附到 0.1 |

所有点要素的 `x / y`、折线的控制点都使用这套坐标。**配置台渲染只读这份坐标，不再查经纬度。**

### 1.2 换算公式

```text
col = floor(x / 12)          row = floor(y / 12)
lon = 99.0   + x / 6912 × 25.5
lat = 42.5   − y / 4320 × 18.3333
x   = (lon − 99.0) / 25.5 × 6912
y   = (42.5 − lat) / 18.3333 × 4320
```

校验例：潼关锚点 `[110.25°E, 34.60°N]` →

```text
x = (110.25 − 99) / 25.5 × 6912 = 3049.4
y = (42.5 − 34.6) / 18.3333 × 4320 = 1861.5
格 = (254, 155)
```

与数据清单中的 `tongguan` 完全一致。面板里的「格 / 经纬度」是派生只读信息，不参与保存。

### 1.3 边界

- 点要素必须满足 `0 ≤ x ≤ 6912`、`0 ≤ y ≤ 4320`；
- 河流 / 山脉的控制点同样必须在图内。内置基线会把投影后越界的点**夹取回图幅**（例如祁连山西端），海岸线用 Sutherland–Hodgman 裁剪；
- 图幅最外圈另有 3 格行军禁带（`MAP_EDGE_MARGIN`），属于玩法约束，不属于本配置文档。

## 2. 顶层文档

```json
{
  "meta": {
    "schema": "sanguo.map-config",
    "version": 1,
    "title": "三国霸业 · 大地图配置",
    "cols": 576,
    "rows": 360,
    "tile": 12,
    "lonRange": [99, 124.5],
    "latRange": [24.1667, 42.5],
    "updatedAt": "2026-10-31T12:40:33.134Z"
  },
  "coastline": [{ "x": 6123.4, "y": 645.2 }],
  "cities": [],
  "passes": [],
  "ferries": [],
  "rivers": [],
  "ranges": [],
  "lakes": [],
  "roads": []
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `meta.schema` | 字面量 | 固定 `sanguo.map-config`，导入时校验 |
| `meta.version` | 字面量 | 当前 `1`；破坏性变更时递增并提供迁移 |
| `meta.title` | string | 文档标题，生成图标题块使用 |
| `meta.cols / rows / tile` | number | 必须为 `576 / 360 / 12`，否则拒绝导入 |
| `meta.lonRange / latRange` | `[number, number]` | 投影区间，记录用 |
| `meta.updatedAt` | ISO string | 保存时刷新 |
| `coastline` | `XY[]` | 陆地闭合环，≥ 3 点 |
| `cities` | `CityNode[]` | 城池 |
| `passes` | `PassNode[]` | 关隘与小径 |
| `ferries` | `FerryNode[]` | 渡口 |
| `rivers` | `RiverNode[]` | 河流折线 |
| `ranges` | `RangeNode[]` | 山脉折线 |
| `lakes` | `LakeNode[]` | 湖泊椭圆 |
| `roads` | `RoadNode[]` | 城际路网，只存端点引用 |

id 全局唯一，前缀约定：`city-* / pass-* / ferry-* / river-* / range-* / lake-* / road-*`。城池与关港沿用运行时 id（如 `changan`、`tongguan`、`mengjin`），便于与配表对齐；新增元素由配置台按「前缀 + 最小空闲序号」生成。

## 3. 数据结构

### 3.1 城池 `CityNode`

```ts
interface CityNode {
  id: string;
  name: string;
  x: number;
  y: number;
  size: 'capital' | 'large' | 'medium' | 'small';
  terrain: 'plain' | 'mountain' | 'forest' | 'water';
  ownerId: string | null;
  isWaterCity: boolean;
  fortification: number;
  note: string;
}
```

| 字段 | 类型 | 范围 / 单位 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 1–64 字符 | 稳定标识；城池沿用配表 id |
| `name` | string | 1–32 字符 | 地图与面板显示名 |
| `x / y` | number | 0–6912 / 0–4320 | 3×3 城郭中心 |
| `size` | enum | 都城 / 大城 / 中城 / 小城 | 决定驻军上限与图标半径 |
| `terrain` | enum | 平原 / 山地 / 林地 / 水乡 | 战场模板与地形适配 |
| `ownerId` | string \| null | 势力 id | `null` 表示无主 |
| `isWaterCity` | boolean | — | 是否按水城处理 |
| `fortification` | number | 0–100 | 城防；≥85 天险，≥70 易守难攻，≥55 城防坚固，≥40 一般 |
| `note` | string | ≤ 400 字符 | 设计备注，不参与运行时 |

示例（新野）：

```json
{ "id": "xinye", "name": "新野", "x": 3578, "y": 2250.3,
  "size": "small", "terrain": "plain", "ownerId": "liubei",
  "isWaterCity": false, "fortification": 42, "note": "" }
```

### 3.2 关隘 / 小径 `PassNode`

```ts
interface PassNode {
  id: string;
  name: string;
  x: number;
  y: number;
  kind: 'pass' | 'trail';
  tier: 1 | 2 | 3;
  edges: Array<[string, string]>;   // 覆盖的道路，空数组 = 未绑定
  guardCityId: string | null;
  extraDays: number;
  fortification: number;
  garrison: number;
  gold: number;
  food: number;
  note: string;
}
```

| 字段 | 类型 | 范围 / 单位 | 说明 |
| --- | --- | --- | --- |
| `kind` | enum | `pass` / `trail` | 关隘可驻守可封锁；小径永远可通行 |
| `tier` | 1 \| 2 \| 3 | 大 / 中 / 小 | 规模档位；数值应在 `BALANCE.GATE.TIER` 区间内 |
| `edges` | `[string,string][]` | 城池 id 对，≤ 8 条 | 关防覆盖的道路。关墙方向、门洞朝向与 A→P→B 折线都由它推；空数组表示未绑定，结构重建会跳过（§5.4） |
| `guardCityId` | string \| null | 城池 id | 法理归属城；关港易手随之易手，`null` 为无主 |
| `extraDays` | number | 0–30 日 | 通过时额外消耗的行军日 |
| `fortification` | number | 0–100 | 关防工事，参与攻关守备 |
| `garrison` | number | 0–20000 | 满编守军；被攻占后按残编接管 |
| `gold / food` | number | 0–500 / 0–1000 | 每月解送给法理城 |
| `note` | string | ≤ 400 字符 | 设计备注 |

示例（潼关）：

```json
{ "id": "tongguan", "name": "潼关", "x": 3049.4, "y": 1861.5,
  "kind": "pass", "tier": 1,
  "edges": [["changan", "hongnong"], ["changan", "luoyang"]],
  "guardCityId": "changan",
  "extraDays": 3, "fortification": 18, "garrison": 3000,
  "gold": 44, "food": 120, "note": "关中东大门，扼守长安—洛阳大道" }
```

### 3.3 渡口 `FerryNode`

```ts
interface FerryNode {
  id: string;
  name: string;
  x: number;
  y: number;
  tier: 1 | 2 | 3;
  edges: Array<[string, string]>;
  riverId: string | null;
  pairId: string | null;
  guardCityId: string | null;
  waterBattle: boolean;
  extraDays: number;
  fortification: number;
  garrison: number;
  gold: number;
  food: number;
  note: string;
}
```

在关隘字段之外，渡口多四个关系字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `edges` | `[string,string][]` | 渡口覆盖的道路；决定渡线走向与两端滩头，未绑定则结构重建跳过 |
| `riverId` | string \| null | 所属河流；用于面板分组与「渡口是否贴着这条河」的提示 |
| `pairId` | string \| null | 对岸渡口 id；两岸图标应分居江面两侧，避免同格渡线 |
| `waterBattle` | boolean | 由此渡口发起的战斗是否按水战处理 |

渡口的图标坐标应落在**岸上滩头**，不是江心；通行线两端都要能沿陆路走到城池。配置台会按文档自身的海岸线 / 湖泊 / 河流几何做实时贴岸检查（§5.1）；运行时 `npm run map:gates` 仍会在 576×360 地形栅格上做最终判定。

> **基线现状**：内置基线的渡口坐标直接取 `GATE.anchor`（渡线中点），30 处里有 27 处触发贴岸提示（23 处图标在江心，4 处离岸超过 2 格）。地形体检会逐条提示，把图标拖到岸上即可消除；这不是校验误报，而是旧锚点与「图标在岸」口径的差异。

示例（孟津渡）：

```json
{ "id": "mengjin", "name": "孟津渡", "x": 3618.6, "y": 1802.6,
  "tier": 1, "edges": [["luoyang", "hemei"]],
  "riverId": "huanghe", "pairId": "heyang",
  "guardCityId": null, "waterBattle": true,
  "extraDays": 2, "fortification": 8, "garrison": 1800,
  "gold": 28, "food": 110, "note": "" }
```

### 3.4 河流 `RiverNode`

```ts
interface RiverNode {
  id: string;
  name: string;
  width: number;
  points: XY[];   // 上游 → 下游，≥ 2 点
  note: string;
}
```

| 字段 | 类型 | 范围 | 说明 |
| --- | --- | --- | --- |
| `width` | number | 8–400 世界单位 | 河面总宽；约 0.7–33 格。干流 90–110，支流 60–80 |
| `points` | `XY[]` | ≥ 2 | 折线控制点；配置台可拖顶点、追加、删除、整体反向 |

河流宽度直接决定渲染江面与「不可通行河岸带」的视觉口径。现基线 7 条：渭水、淮水、汉水、湘水、赣水、黄河、长江；干流宽 90，支流 70–76。数据清单里有每条河的全部路径点。

### 3.5 山脉 `RangeNode`

```ts
interface RangeNode {
  id: string;
  name: string;
  width: number;
  height: number;
  points: XY[];   // 山脊折线，≥ 2 点
  note: string;
}
```

| 字段 | 类型 | 范围 | 说明 |
| --- | --- | --- | --- |
| `width` | number | 8–600 世界单位 | 山地带宽（核心山体 + 两侧丘陵）；秦岭约 336 |
| `height` | number | 0–1 | 视觉高度，影响山脊符号与色阶 |
| `points` | `XY[]` | ≥ 2 | 山脊走向；控制点越密，山形越贴合 |

山脉在配置台里画成「半透明山带 + 山脊线 + 横向短线」，不是最终美术；它用于确认山脊走向和山口位置。

### 3.6 湖泊 `LakeNode`

```ts
interface LakeNode {
  id: string;
  name: string;
  cx: number;
  cy: number;
  rx: number;   // 东西半径
  ry: number;   // 南北半径
  note: string;
}
```

以椭圆近似，`rx / ry` 为世界单位（现基线 68–179 / 47–156；洞庭最大，巢湖最小）。选择椭圆而不是多边形，是因为湖岸没有战略细节，五个大湖用椭圆足够，且编辑成本最低。

### 3.7 路网 `RoadNode`

```ts
interface RoadNode {
  id: string;
  from: string;
  to: string;
  cost: number;
  wild: boolean;
  note: string;
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `from / to` | 城池 id | 端点必须存在；不允许自环 |
| `cost` | 1–20 | 抽象代价，只用于路网排序，不是行军 MP |
| `wild` | boolean | 险道：可行军，但不计「邻城」 |

路网不存几何，渲染时按两端城池坐标连直线。关隘 / 渡口通过自身坐标落在某条道路附近来表达「咽喉」，不在道路里存中间节点。

### 3.8 海岸线 `coastline`

`XY[]` 闭合环，由海岸线控制点 + 图幅左边 / 上边闭合而成，南缘按纬度下限裁剪。共 43 点。v1 配置台不提供海岸线编辑 UI，避免 43 个点的手工拖拽；需要改海岸线时编辑基线 JSON 后导入，或继续修改 `geography.ts` 的 `COASTLINE` 重新生成。

## 4. 数值档位与约束

### 4.1 枚举

| 枚举 | 取值 | 显示 |
| --- | --- | --- |
| `CitySize` | `capital / large / medium / small` | 都城 / 大城 / 中城 / 小城 |
| `CityTerrain` | `plain / mountain / forest / water` | 平原 / 山地 / 林地 / 水乡 |
| `PassKind` | `pass / trail` | 关隘 / 小路 |
| `Tier` | `1 / 2 / 3` | 大型 / 中型 / 小型 |

### 4.2 关港档位区间（`BALANCE.GATE.TIER`）

| 类型 | 档位 | 工事 | 守军 | 月金 | 月粮 | 额外行军日 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 关隘 | 大型 | 15–18 | 2600–3200 | 38–46 | 100–125 | 3 |
| 关隘 | 中型 | 9–13 | 1700–2300 | 24–32 | 60–90 | 2 |
| 关隘 | 小型 | 6–9 | 1300–1700 | 15–23 | 40–60 | 2 |
| 渡口 | 大型 | 8–12 | 1700–2200 | 26–36 | 100–145 | 2 |
| 渡口 | 中型 | 5–7 | 1200–1600 | 18–24 | 80–100 | 2 |
| 渡口 | 小型 | 4–6 | 900–1300 | 14–18 | 55–80 | 2 |

配置台对关港数值只做**全局范围**校验（工事 0–100、守军 0–20000、月金 0–500、月粮 0–1000），不强制落在档位区间。档位是配平口径：把数据合并回运行时前，应跑 `tests/gates.spec.ts` 复核 `BALANCE.GATE.TIER` 区间。

### 4.3 其他建议区间

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 城池间距 | ≥ 2 格（24 世界单位） | 配置台对更近的城对给 warn；3×3 城墙需要落位空间 |
| 河流宽度 | 干流 80–110，支流 60–85 | 水军能展开，又不吞掉半屏陆地 |
| 山脉带宽 | 主干 240–390，支脉 80–160 | 形成需要绕行的战略阻隔 |
| 湖泊半径 | 100–200 | 给沿岸城池留出完整 3×3 落位 |
| 关隘位置 | 山脊 / 丘陵窄口 | v1 不校验地形，需配合 `npm run map:diag` |
| 渡口位置 | 江面附近、图标在岸 | 同上，贴岸检查由 `map:gates` 完成 |

## 5. 校验规则

导入时跑两层校验：**zod 结构校验** + **业务校验**；编辑期间实时跑业务校验，用于面板提示。

| 级别 | 规则 | 处理 |
| --- | --- | --- |
| error | `meta.schema / version / 幅面` 不匹配 | 拒绝导入 |
| error | 文档标题 / 元素名称为空 | 拒绝导入与保存 |
| error | 坐标越界、湖泊半径 ≤ 0 | 拒绝导入 |
| error | 河流 / 山脉少于 2 个控制点 | 拒绝导入 |
| error | id 重复 | 拒绝导入 |
| error | 海岸线少于 3 点 | 拒绝导入 |
| warn | 道路端点不存在 / 自环 | 允许，面板提示 |
| warn | 渡口的 `riverId / pairId / guardCityId` 断引用 | 允许，面板提示 |
| warn | 关隘的 `guardCityId` 断引用 | 允许，面板提示 |
| warn | 两城相距 < 2 格 | 允许，面板提示 |

配置台顶部与底部状态条实时显示错误数；「配置概览」列出前 6 条。warn 不会阻止保存，因为紧凑城对、暂时断引用是编辑中间态。

### 5.1 地形体检（编辑期）

地形校验只看**配置文档自身**的几何，不读运行时 `terrainGrid`：挪一条河、加一条山脊，结论立刻变化。

| 元素 | 规则 | 判定 |
| --- | --- | --- |
| 关隘 / 小径 | 必须在水域外 | 落在海 / 湖 / 河里 → warn |
| 关隘 / 小径 | 到最近山脊中心线的距离 ≤ `带宽 + 2 格`（24 世界单位） | 超出 → warn「不贴山」 |
| 渡口 | 图标必须在陆地 | 落在海 / 湖 / 河里 → warn |
| 渡口 | 到最近水缘的距离 ≤ 2 格（24 世界单位） | 超出 → warn「离岸太远」 |

- 水域：海岸线外、湖泊椭圆内、河流折线半宽内；湖泊优先于穿湖而过的河段。
- 山地：距山脊 ≤ 带宽/2 为核心，≤ 带宽为丘陵；贴山判定再外扩 2 格容差。
- 级别统一为 **warn**：地形是编辑期提示，不阻止保存。真正的山口 / 渡线放行条件仍以 `map:gates` 为准。
- 面板表现：地图金三角角标、左侧「仅问题」清单、右栏「地形校验」卡（显示最近山脊 / 水缘的实测距离）。
- 数据清单的「地形」列由同一套规则生成；`⚠` 只提示，不影响基线 JSON。
- **基线现状**：内置基线有 28 条地形提示（潼关锚点在渭水河口的水面内；渡口 27 条，其中 23 处图标在江心、4 处离岸超过 2 格）。这是数据现状，不是校验器误报。

### 5.2 严格校验（运行时地形）

按需加载 `render/terrainGrid` 的 576×360 栅格（首次约 0.3–0.5 秒，之后缓存），用与 `npm run map:gates` 相同的地形尺子做**点位级**采样：

| 元素 | 严格规则 | 失败示例 |
| --- | --- | --- |
| 关隘 / 小径 | 所在格必须是 `mountain` / `hill`，不能是水面或城墙 | 潼关落在河里（254,155） |
| 渡口 | 所在格必须是陆地；2 格内有水面；八方向存在 ≥4 格连续水面 | 孟津渡图标在河面；延津 2 格内无水 |
| 成对渡口 | 两图标连线上的连续水面 ≥4 格，否则视为同岸 | 淮阴渡 / 泗口渡连续水面 0 格 |

- 入口：地图右上「严格」开关，或概览「运行严格校验」；加载后拖动 / 改坐标会实时重算。
- 严格校验读 `geography.ts` 生成的**运行时地形**，不随面板里改河流 / 山脊变化；改点位才会改变它。跟随文档山川的是编辑期几何校验（§5.1）。
- 表现：红色三角角标、左栏红点、「严格校验」独立清单；与编辑期金色 warn 分开计数。
- 级别：不阻塞保存；它是合并回运行时之前的最后一道地形体检。
- **这是采样版**：只判点位所在格的地形与对岸，不重建关墙 / 门洞 / 通行线。要跑结构检查用 §5.4。
- **基线现状**：严格校验 32 条（5 处关隘 / 小径地形不符：1 处落水、4 处平原；27 处渡口，其中淮阴 / 泗口 1 对同岸）。

### 5.3 一键吸附

| 范围 | 入口 | 行为 |
| --- | --- | --- |
| 单点 | 右栏地形卡「吸附到岸 / 山脚」 | 在 240 世界单位内做环形搜索，取最近合法点 |
| 批量 | 概览「一键吸附 N 处」两次确认 | 对「地形 + 严格」的并集逐点吸附，写入一步撤销历史 |

- 候选必须同时通过编辑期几何（§5.1）与**已加载的**严格校验（§5.2）；严格校验未运行时只按几何吸附。
- 岸别用**河段法向**：逐段取切向，沿折线做定向传播（相邻切向点乘为负就翻转），河拐弯时法向跟着拐；不再用整条河首尾连线定向。湖泊用「湖心 → 渡线中点」的径向法向，两者都是岸线外法向。
- 成对渡口取两港中点处**同一个参照系**判岸，两侧必须落在法向的正负两边；分侧之后还要过一遍「两点之间连续水面 ≥ 4 格」，避免分属两侧却沿湖岸绕成一片陆地。
- 批量吸附把成对渡口作为一组处理：两侧联合搜索，位移和最小且确实跨水的那一对胜出。
- **当前基线实测**：并集 33 处，批量吸附 32 处，地形提示清零，严格校验清零（含淮阴渡 / 泗口渡，跨洪泽湖 8 格水）。

### 5.4 结构重建（lane / wall，面板版 `map:gates`）

按文档坐标重新砌关墙、落关港，跑与 `npm run map:gates` **同一份规则**（`render/gateAudit.ts`，脚本与面板共用）：

| 检查 | 内容 |
| --- | --- |
| R7 关隘 | 中心格是山地 / 丘陵；关墙存在、门洞与中心一致；墙格全为山岭；墙端是山 / 水 / 图边；A→P→B 折线 ≤ 1.8 × 直线 |
| R8 渡口 | 中心格是水面；图标格在岸；渡线跨 ≥ 4 格水；图标落在两端滩头之一 |
| 通行线 | 非空、4 邻接、含中心格、在图内、不压城墙、关港之间不重叠 |
| 对岸 | 成对港口锚点错开 ≥ `PAIR_MIN_OFFSET`；图标分居两岸 |

- 入口：概览「结构重建」。同步阻塞约 0.6–1.5 秒（重算 576×360 地形 + 砌 17 道关墙 + 落 47 处关港），先画 loading 再执行。
- 前置：每个关港要有 `edges`。未绑定的会被跳过并列进 `skipped`，不再静默按道路中点猜。
- 表现：地图叠加层 —— 青绿小方块 = 通行线格，空心方框 = 重建后的门洞 / 滩头；与文档点位错开时一眼可见。
- 右栏「关防结构」卡：落位格、通行线长度、文档 → 落位偏差；关隘偏差 ≥ 6 单位时可「采用落位坐标」，把文档点位挪到门洞上。
- **渡口不给回填按钮**：渡口点位同时是运行时渡线锚点，图标由渡线推出。把点位改成图标会让下一次重建从岸边重新找渡线 —— 实测 30 处里 10 处会移 1–2 格，洞庭渡还会退化到只跨 2 格水。要改渡口，直接拖点位或「吸附到岸」，再看结构卡核对落位。
- **它不改文档**：重建只是体检。改完点位要重新跑一次；文档一改，概览标「已过期」。
- 重建会改写全局地形栅格，结束后立即恢复运行时地图，所以「严格校验」读到的仍是运行时地形。
- **基线实测**：47 处落位、17 道关墙、0 项问题、0 失败、约 0.6 秒。

### 5.5 一键回写配表

`npm run map:apply` 把文档写回 `src/data/tables/`：

| 项 | 说明 |
| --- | --- |
| 输入 | 默认 `docs/大地图配置基线-v1.json`，`--doc path` 可换（配置台「导出 JSON」的产物） |
| 回写 | `gates.ts`：`anchor`（世界坐标反算经纬度）、`name`、`tier`、`extraDays`、`fortification`、`gold`、`food`、`garrison`；`geography.ts`：`CITY_COORDS` |
| 模式 | 默认 dry-run 只打印改动；`--write` 才落盘，先写 `.bak` |
| 容差 | 经纬度差 ≤ 0.001°（≈ 0.27 世界单位）视为未变，滤掉世界 ↔ 经纬度往返噪声 |
| 不追加 | 文档新增、配表没有的关港只列出来，需要人工补 `kind / tier / edges / 数值` |
| 不删除 | 配表有、文档已删的只提示，脚本不动数据 |
| 不回写 | 河流 / 山脉 / 湖泊 / 海岸线：它们决定整张地形，改一条河会重算所有关墙与城池落位，必须单独走一轮 `map:gates` + 全量测试 |
| 岸上锚点提醒 | 渡口点位落在陆地时单独列出：回写后运行时会从岸边重新找渡线，落位可能移 1–2 格 |

回写后按提示跑 `npm run map:doc && npm run map:gates && npm test`。

> **首次回写实测**：5 处渡口（白马津 / 延津 / 赤壁渡 / 瓜洲渡 / 白帝渡）原本没有 `anchor`，落位靠道路中点推；回写把它们钉成显式锚点，落位不变，`map:gates` 仍通过。写完再跑一次 dry-run 输出「配表已与文档一致」，回写是幂等的。

## 6. 持久化

| 项 | 约定 |
| --- | --- |
| 浏览器存档 | `localStorage["sanguo.map-config.v1"]` |
| 保存动作 | 顶栏「保存」或 `⌘S / Ctrl+S`；显式保存，写盘前跑完整校验，空名称 / 越界会阻止落盘 |
| 未保存保护 | `beforeunload` 拦截；顶栏显示「● 有未保存修改」 |
| 正式产物 | 「导出 JSON」→ `sanguo-map-config-v1-YYYYMMDD-HHmm.json` |
| 恢复 | 刷新页面自动读本地存档；「导入」读 JSON |
| 重置 | 「重置为内置基线」，只改内存，仍需保存才落盘 |
| 版本 | `meta.version = 1`；当前解析器拒绝其他版本，升级时补迁移 |

**这不是玩家存档。** 玩家进度仍在 IndexedDB 的 `SaveSlot` 里；本配置文档只服务地图编辑与出图，不参与游戏内回合结算。

保存后顶栏显示「已保存 · HH:mm」，右侧概览的「更新时间」同源。生成地图时：

- 有本地存档 → 用存档渲染；
- 有未保存修改 → 明确提示「预览使用上一次保存的存档」；
- 从未保存 → 用内置基线，并提示。

## 8. 与运行时配表的关系

内置基线由以下表投影生成（`src/studio/seed.ts`）：

| 文档字段 | 来源 | 说明 |
| --- | --- | --- |
| `cities` | `CITY_TABLE` + `CITY_COORDS` | 名称 / 规模 / 归属 / 城防来自城池表，坐标由经纬度投影 |
| `passes` | `GATES`（`pass` / `trail`） | 位置优先取 `anchor`，否则取道路两端中点；`edges` 原样带出；数值直接落表 |
| `ferries` | `GATES`（`port`） | 同上；`riverId` 由最近的河流折线推断（≤ 320 世界单位）；`pairId` / `waterBattle` 原样带出 |
| `rivers` | `RIVERS` | `width = riverWorldWidth(scale)`，点为经纬度投影 |
| `ranges` | `RIDGES` | `width = 半宽 × 2 × 每经度世界单位` |
| `lakes` | `LAKES` | 中心投影，半径按经纬两个方向换算 |
| `coastline` | `COASTLINE + LAND_FRAME` | 投影后裁剪到图幅 |
| `roads` | `MAP_EDGES` | 115 条城际边，`wild` 原样保留 |
| `meta` | 常量 | 576×360、格宽 12、经纬区间 |

**边界：浏览器只导出 JSON，写盘一律走 Node 脚本。** 浏览器工具直接改源码会绕过类型检查与测试，所以回写放在 `scripts/map-apply.ts`（可 dry-run、可 diff、可 review）。

推荐流程：

1. 配置台调整 → 「结构重建」确认落位 → 保存 → 导出 JSON；
2. `npm run map:apply`（默认 dry-run）审阅要改的字段；
3. `npm run map:apply -- --write` 落盘（自动 `.bak`）；
4. `npm run map:doc && npm run map:gates && npm test`。

回写只覆盖点位与数值；山川湖泊要改，走 `RIVERS` / `RIDGES` / `LAKES` 人工合并 + 全量重跑（§5.5）。
