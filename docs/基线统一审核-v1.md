# 基线统一审核 v1

> 审核对象：`README.md`、`docs/` 的 19 份设计文档 + 归档 7 份 + 2 份生成物（数据清单 / 基线 JSON）、
> `核心数值总表-v2.html`，以及 `src/`（约 5.3 万行）与 `tests/`（63 文件）。
> 审核时间：2026-10-31。方法：**以代码为真值**，逐条比对文档断言；能跑的跑一遍（typecheck / test / map:check / map:gates）。

## 0. 结论

文档与代码的脱节不是零散笔误，是**结构性的**：同一组数字（地图尺寸、关港数量、版本号、测试规模）
在 README、规格、迭代计划、数值总表里各抄了一份，地图一改就四处飘。审核共确认 **14 项偏差**，
其中 3 项会直接导致错误决策（按规格写迁移、按总表查关防、按文档写存档迁移）。

处置：修 13 项，登记 1 项待裁决（字段命名）；另有 2 项内容债与 1 项判据校准见 §3.2 / §4。
并补上**机器校验**（`npm run baseline:check`，已并入 `verify`），
让「代码改了、文档没改」从「靠自觉」变成「构建失败」。

## 2. 根因

1. **三份「真值源」并列。** README 有一张文档表，迭代计划 §13 有一张真值源表，archive 里还有一张。
   三张表互相不引用，谁都可以自称有效。
2. **生成物只覆盖一半。** `map:doc` 覆盖地图配置，`table:sync` 只覆盖武将；关防、城池、剧本在总表里是手写快照。
3. **没有校验。** 数字对不对，只能靠人读。地图从 432 行裁到 360 行时，代码改了、文档没改，没有任何东西会红。
4. **门禁会假绿。** `npm test` 少跑两个文件时仍然打印 `Test Files 61 passed`，只有 `Errors` 行提示异常。
   这解释了为什么「579 项」这个正确数字反而没人敢信——**跑出来的数一直是 559**。

### 3.2 判据校准（改了测试，必须说明）

`tests/gates.spec.ts` 判断「两港是否同岸」用的是**纯陆路 BFS 步数 ≤ 60**。
实测 13 组配对：12 组河港之间根本没有陆路（400 步内不可达），只有两组湖港有绕行——
巴陵↔洞庭 43 步、柴桑↔鄱阳 252 步。真正同岸的旧 bug（采石/横江）沿岸只有 20 步以内。

所以 60 步的分界太松，会把「绕湖 43 步」误判成同岸。阈值收紧到 **30 步**，
并在用例里写明依据。这不是为了让数据过关——**巴陵/洞庭 是真实对岸**，43 步绕行也确实是它的弱点，
已登记为内容债（见 §4）。

### 3.3 新增机制

| 产物 | 作用 |
| --- | --- |
| `src/data/baseline.ts` | 基线事实的**唯一采集口**（`collectFacts()`），只采代码能直接读到的事实 |
| `npm run baseline:doc` | 生成 `docs/项目基线-v1.json` 与基线台账的「数据基线」块 |
| `npm run baseline:check` | 三道闸：代码↔JSON、JSON↔台账、文档断言；已并入 `npm run verify` |
| `docs/项目基线-v1.md` | 文档地图 + 数据基线 + 需求契约 + 偏差登记，**唯一台账** |

设计上刻意不做「全自动扫描文档数字」：那需要为每句话写正则，维护成本高于收益。
断言表只覆盖**写错就会导致错误决策**的数字，共 5 组。
