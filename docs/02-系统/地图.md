### 1. 地图规格与旧档迁移

| 项 | v1 | v2 | v3 | v4（当前） |
| --- | --- | --- | --- | --- |
| 栅格 | 96×72 | 192×144 | 576×432 | **576×360**（南缘裁到 24.17°N） |
| 每格世界单位 | 12 | 12 | 12 | **12** |
| 世界尺寸 | 1152×864 | 2304×1728 | 6912×5184 | **6912×4320** |
| `MAP_VERSION` | 1 | 2 | 3 | **4** |
| `SAVE_VERSION` | 3 | 4 | 5 | **6** |

- 经纬度投影不变（`LON_RANGE` / `LAT_RANGE`），只放大采样密度；59 城仍按真实坐标落位，
  但 3×3 城墙的最终格位由 `render/terrainGrid.cityBlocks()` 按地形评分微调，不再允许城墙压水 / 压山。
- 旧档迁移按版本链逐级放大：v1 → v2 → v3 → v4，每一级都把部队坐标乘以对应倍率，
  再吸附到最近的可行陆格；**只放大大地图坐标，不放大战斗内局部坐标**。v4 只裁南缘，比例尺不变。
- 缺 `mapVersion` 的存档一律视为 v1；`SAVE_VERSION` 小于 6 的档走同一套迁移链（v6 起升级清库）。

#### 为什么是 576×432（v4 裁到 360 行后仍成立）

- 城池之间终于能放下"路程"：中原到江陵不再是一屏内的几个点；
- 长江 / 黄河干流约 7–9 格宽、支流约 6–7 格宽，既够摆开两支水军，又不会在近景里吞掉半屏陆地；
- 600% 近景时一格约 65px（1280 宽视口），山道、城门、渡口都能看清；
- 20% 全图仍是完整天下，适合看大势与势力色块。

#### 2.2 通行线

- 每处关港有一条 **1 格宽、4 邻接**的通行线（`GateSite.lane`）；
- 关隘的线穿过山脊，两端接山路；港口的线横渡江面，两端是滩头（`approaches`）；
- 小路的线同样穿过山脊，但没有归属、守军与产出，也无法封锁——它只是"另一条能走的山口"；
- **线外的山体与水面不可通行**：关港是穿越山脉 / 江河的唯一缺口；
- 关隘 / 小路的中心必须在山地 / 丘陵；港口中心必须在水面；
- 港口图标（`GateSite.icon`）必须在岸上，且是两端滩头之一——否则船像停在江心；
- 同一条道路上挂多处关防时，用 `anchor`（经纬度锚点）显式指定先后位置
  （如 汉中–梓潼 一线先过阳平关、再过剑阁），不再取道路中点。

#### 2.3 归属与通行

| 状态 | 判定 | 结果 |
| --- | --- | --- |
| 己方 | `gateOwnerOf(s, id) === 势力` | 自由通过 |
| 无主 | `ownerId == null` | 可通行；路过的部队会顺手接管 |
| 敌对 | 归属其他势力 | **封锁整条通行线**，必须先攻关 |
| 法理城易主 | 关港未独立攻占 | 归属跟随 `guardCityId` 的城主 |
| 独立攻占 | `GateRuntime.ownerId` 存在 | 以关港自身归属为准，不再跟随法理城 |
| 小路 | `kind: 'trail'` | 不参与归属判定，永远可通行、不可封锁 |

#### 2.4 产出、守军与数值档位

- 关港没有内政、不能征兵、不能建造；
- 每月按类型产出少量钱粮，**直接解送给所属势力的法理城**（`gateSupplyCityOf`），
  不进入关防自己的府库；
- 守军按月少量回补，但不能超过关港上限；
- 攻占关港只改变通行权与产出归属，不触发城池易主。

档位区间（`BALANCE.GATE.TIER`，配表逐项落值，`tests/gates.spec.ts` 校验落在区间内）：

#### 2.7 AI

- 行军路径经过敌对关港时，AI 必须先攻关，不能"绕过去"；
- 路过无主关港会顺手接管，避免留下免费通道（小路除外）；
- 关港守军不足时，AI 会从法理城调兵补防。

#### 2.8 关港驻军（v4）

关隘 / 港口除了配表守军，还可以收容真实部队：

| 项 | 规则 |
| --- | --- |
| 入口 | 部队抵近关前（`armyAtGate`）后，在 `GatePanel` 点「驻军」，或派发 `GARRISON_GATE` |
| 表示 | `Army.garrisonGateId`；仍是 `state.armies` 中的真实部队，不复制兵力 |
| 上限 | 一座关港只驻一支；已有驻军时须先撤出 |
| 地图 | 驻军不占地图格、不参与关前野战，也不吃旬移动力回复（`mp = 0`） |

| 易手 | 关港被攻占时，败方驻军退往最近己方城（保留 70% 兵力）；无城可退则溃散 |

小路（`kind: 'trail'`）没有关门，不能驻军，也不能封锁。

### 3. 真渡口判定

港口不是"水边随便一个点"。`gateSites()` 对每个港口做三项检查：

1. 两端滩头（`approaches`）都是可站立的陆地；
2. 两端滩头都能沿陆路走到最近的城池（不被水或山封死）；
3. 两岸之间不存在短陆路绕行——否则这个"渡口"没有存在意义；
4. 成对港口的图标分居两岸，不能并排挤在同一岸。

不满足条件的候选点会被丢弃或沿江平移；`npm run map:gates` 与
`tests/gates.spec.ts` 都会逐项校验。夏口渡、赤壁渡等长江渡口因此落在真正的两岸滩头上，
而不是江心或湖心。

#### 3.1 过河 = 一次摆渡（行军不下水）

**大地图行军时**，陆地部队不会站在水面格上。江 / 湖 / 海在 `marchDaysForArmy` 里一律是 `Infinity`，
渡线本身也不例外；过河是两岸滩头之间的一条**跳跃边**（`ferryHopFrom` / `marchStepDays`）：

| 项 | 规则 |
| --- | --- |
| 通行 | 只能从某港的 A 岸滩头一次渡到 B 岸滩头，反向同理 |
| 耗时 | `extraDays + ceil(渡线水面格数 / 4)` 日，全段一次结算（见 `GateSite.crossDays`） |
| 跨旬 | 本旬付不起船程就停在**近岸滩头**攒天数，绝不进江心 |
| 封锁 | 敌港封锁的是这条跳跃边，与关隘封锁山道同构 |
| 版图 | `territoryEntryCost` 同步把水面设为不可进入，再单独松弛摆渡边 |
| 表现 | 渡线默认不画，只在悬停 / 选中该港时点亮；出征预览里那一段直线就是摆渡 |

例：夏口渡渡线 22 格水面 → 摆渡 8 日；濡须口 8 格 → 4 日。原来的口径是沿渡线逐格
走 1.5 日/格（22 格 ≈ 33 日），部队会在江心连站三旬——这正是本条要消灭的现象。

> **例外：水战。** 一旦进入 `waterBattle`，战棋单位可以乘船站在水面格上，
> 非水军每回合晕船减员；这只发生在战斗内，不改变大地图行军"不下水"的规则。
> 战后非水军胜方会自动上岸（见 §4.3）。

### 4. 全图战斗

#### 4.1 攻城战（v3）

- 新战斗 `mapBattle: true`，`BattleState.grid` 变为可选；
- 战场就是 576×360 大地图，使用**绝对格坐标**，不再裁切 12×8；
- 攻方在目标城门外 2 格列阵，守方在 3×3 城墙内展开；
- 旧存档里的战斗仍保留 `grid`，走兼容分支，不强制迁移；
- 地形、城防、ZOC、兵种相性、计策、溃散、俘虏等规则沿用原战斗系统；
- 寻路改为预计算 `MarchGrid`：Dijkstra 只做数值访问，目标已知时提前结束，
  避免每帧对 576×360 全图跑一遍。

#### 4.2 行军遭遇战（v4）

`createFieldBattle(state, attackerArmyId, defenderArmyId)` 负责把两支相邻的行军纵队
直接转成一场 `BattleState`：

| 项 | 规则 |
| --- | --- |
| 条件 | 双方都是地图部队（非关港驻军）、敌对、可战、曼哈顿距离 ≤ 1 |
| 类型 | `kind: 'field'` + `field: { x, y, attackerArmyId, defenderArmyId, attackerAt, defenderAt, water }` |
| 落位 | 从双方当前格向外找空地列阵；不搬进任何城池，也不生成 12×8 战场 |
| 画面 | `BattleScreen` 对 `mapBattle` 统一渲染 `MapCanvas`，镜头聚焦接战中心；`BattleCanvas` 只作旧存档 fallback |
| 不占城 | 野战不读写城池归属，`targetCityId` 只借来提供文案 / 撤退城市线索 |
| 玩家入口 | 地图 HUD 的「攻击敌军」按钮 → `ATTACK_ARMY` |
| AI 入口 | AI 行军后与玩家相邻 → 自动 `createFieldBattle` 并暂停大地图；AI 互殴走无随机数的轻量战力结算，不弹战棋 |

结算（`resolveFieldBattle`）：

- 胜方纵队留在原地，回写兵力 / 经验 / 忠诚，清空路径，`mp = 0`；
- 败方纵队从 `state.armies` 移除，未溃散武将退往**最近己方城**，保留 70% 兵力；
- 无城可退时主将被俘、副将溃散；
- 战报标题按玩家视角区分「野战胜利 / 野战失利 / 遭遇战失利 / 击退敌军」。

#### 4.3 水战（v4）

接战点、攻方所在格或守方所在格任一为水面，即 `waterBattle: true`：

| 项 | 规则 |
| --- | --- |
| 通行 | 所有兵种都可进入水面（乘船）；平时只有水军能走水面 |
| 移动 | 水战水面：水军 1 MP，非水军 2 MP |
| 减员 | 非水军滞留水面，每回合损失 5% 兵力（至少 1 兵），水军不受影响 |
| 落位 | 优先在水面找列阵格，水面不足才退到岸上，保证任何地形都能开战 |
| 战后 | 非水军胜方若仍在江心，自动移到最近可行军陆地，避免下一旬从水面起步 |
| 城池 | 水战同样不占城；港口驻军与关港归属仍按关防规则结算 |

#### 4.4 城墙在野战中的边界

野战借道城郊时，城墙只是障碍：`battleTerrainAt` 不把目标城城墙算作 `city`，
`reachableTiles` 也禁止野战单位踏上任何城墙格。只有 `kind: 'city'` 的攻城战
才允许站上目标城城墙、逐日磨损耐久。

#### 5.1 缩放口径

| 缩放 | 用途 | 说明 |
| --- | --- | --- |
| 20% | 全图 | 使用全图总览缓存，看势力色块与大势 |
| 100% | 州郡总览 | 一格约 11px（1280 宽视口），适合看路网与军团走向 |
| 300% | **默认作战视角** | 一格约 33px，城池、关港、部队与战棋单位都清晰可点 |

`CAMERA_BASE = 5`，`MIN_ZOOM = 0.2`，`DEFAULT_ZOOM = 3`，`MAX_ZOOM = 6`，
`ZOOM_STOPS` 共 15 档（20% / 30% / 45% / 65% / 85% / 100% / 125% / 160% / 200% / 250% / 300% / 320% / 400% / 500% / 600%），
语义四档为 20% 全图 / 100% 州郡 / 300% 作战 / 600% 近景。

#### 5.2 地形分块

- 世界 6912×4320，整图缓存即使 0.5× 也要约 60MB，移动端会触发 canvas 上限；
- **两档缓存**（I7 · 7.5 定稿）：
  - 粗档 **384×384 世界单位一块、1.5× 分辨率、LRU 32 块**（约 42MB），`zoom < 3.2` 使用；
  - 细档 **144×144 世界单位一块、3× 分辨率、LRU 16 块**（约 12MB），`zoom ≥ 3.2` 使用。
    全图切成 48×30 = 1440 块，高倍率视野（约 400×310 世界单位）只覆盖两三块，周转得过来；
- 高倍率时粗档先铺满视野、细档叠在上面：细档未烘完时看到的是"略糊但完整"的地形，不是空洞；
- 补烘节奏：单帧预算粗档 6 块 / 细档 2 块；两次绘制间隔 < 110 ms 视为连续操作，暂停补烘；
  补烘间隔 160 ms（必须大于 110 ms，否则补烘帧会把自己判成"连续操作"，永远烘不出来）；
- 低倍率全图直接使用单独的总览缓存（1/10 分辨率）。

#### 5.3 美术要点

- **河流**：宽度微起伏的平滑绢带 + 上下游色差 + 裁剪内的深浅斑 / 碎波 / 岸沫，
  不再使用多层等宽描边；深浅斑用径向渐变，边缘自然淡出，避免"水面网格"与椭圆硬边；
- **山脉**：`Massif` 山体成块，前后错落；丘陵用扁缓山包，沟壑用暗色折线；
- **关隘**：两座山包 + 沿山道的岩壁 + 土路 + 碎石 / 裂纹，关门嵌在山口里；
- **港口**：图标落在岸上滩头，渡线默认不画，只在悬停 / 选中该港时以虚线亮起；
- **道路**：城池之间不画驿道线（`state.edges` 只供 AI / 议会算路），
  行军是逐格走的，底图上再拉一层线会把山水读成拓扑图。

#### 5.4 版图染色与名牌（I7 · 7.2 / 7.6 定稿）

**染色**（`render/territoryPaint.ts`）：

- 铺色 2 px/格、模糊 1.8px；墨线单独 **3 px/格、模糊 1.2px**（近景才不糊），合计约 17MB；
- 势力色先向白色提亮 **28%**，再用 **`color` 混合**（取势力色色相/饱和度、保留宣纸明暗）。
  旧方案 multiply 会把深蓝、深绿压成灰紫，已在 30% / 100% / 600% 三档真机对比后替换；
- 墨线仍用 multiply（宿墨压深纸底，是线不是面）；
- 染色强度 `territoryWash`：20% → 0.71，100% → 0.42，200% → 0.26，≥300% 封底 0.10。

**名牌**（`render/labelLod.ts`）：

| 档位 | 倍率 | 显示 |
| --- | --- | --- |
| 0 | < 0.45（全图） | 仅都城 |
| 1 | 0.45–0.95 | + 大城 |
| 2 | 0.95–2（州郡） | + 中城 / 小城 / 关港名 / 「势力 · 兵力」副行 |
| 3 | ≥ 2（近景） | 全部 |

- 选中 / 悬停的城无论档位都带名牌；名牌仍按 2px 碰撞盒避让；
- 命中框：城池按"离城心至少 18px"外扩（低倍率小城自动变大，仍取最近中心，不误点邻城）；
  关港命中半径 14px，390px 手机可点选。

### 8. 已知取舍

1. **关港通行线是运行时生成的**：配表只写档位、锚点与法理城，`render/gateGrid.ts`
   按地形找山口 / 渡线；新增关港需要维护 `anchor`、`guardCityId` 与配对关系，
   并由 `map:gates` 校验落位。
2. **水战是"简化舟师"而非独立舰队系统**：所有兵种都能乘船，水军只保留 1 MP 与免晕船优势，
   没有独立舰船、阵型与接舷战；这保证任何江面遭遇都能直接开打，但深度仍低于专门水战作品。
3. **旧战斗存档不迁移局部坐标**，只保证能继续打完；新战斗一律走大地图。
4. **地形分块在高倍率仍有轻微模糊**：细档 3× 放大到 600% 约 1.8 倍（粗档为 2.2 倍），
   属于性能与清晰度的折中；再想更锐需要按设备像素烘焙或改用 WebGL。
5. **粮食无上限后，后期粮草可能大量堆积**；目前只靠运输与出征消耗，没有新的仓储机制。
6. **编队只在出征 / 行军端自动成队**：目前没有独立的"布阵界面"，玩家不能逐场手动改副将。

### 9. 武将五维与队伍编制

#### 9.1 五维口径（参考《三国志 11》）

`General` 持有 `leadership`（统率）、`force`（武力）、`intellect`（智力）、
`politics`（政治）、`charm`（魅力），取值 0–100；名将数值写在
`data/tables/generalStats.ts`，补位将领按武力 / 智力折算，保证全员五维完整。

| 属性 | 作用 |
| --- | --- |
| 统率 | 带兵上限的主属性；出征时决定默认主将排序 |
| 武力 | 普攻伤害、单挑、突击 |
| 智力 | 计策成功率与计策减伤 |
| 政治 | 内政 / 外交面板数值（展示与 AI 参考） |
| 魅力 | 登用 / 征兵 / 民忠面板数值（展示与 AI 参考） |

带兵上限公式：

```
带兵上限 = 统率 × 10 + 武力 × 8 + 智力 × 4 + 等级 × 80
```

`tests/formulas.spec.ts` 锁定样例：1 级吕布（统 89 / 武 100 / 智 26）= 1874，
1 级诸葛亮（统 92 / 武 38 / 智 100）= 1704。

#### 9.2 队伍编制：1 主将 + 2 副将

- 一支队伍最多 `BALANCE.SQUAD_DEPUTIES_MAX = 2` 名副将（`systems/squads.ts`）；
- **战场上一个队伍只占一个单位**：兵力合并，武力 / 智力取队内最高，
  兵种与移动力跟随主将；
- 战后按**出阵兵力份额**把剩余兵力分回各将，副将不会凭空消失；
- 编队配置是可选参数（`createBattle(..., { squads })` / `sortieArmy(..., squads)`）：
  不传时保持"一将一队"，旧测试与旧档行为不变；
- 出征时未显式配置，则按统率从高到低每 3 人一队自动成队；
- `BattleScreen` 单位卡显示"副将 关羽、张飞"，`RosterDialog` / 城将列表显示完整五维。

单次出征仍最多 5 名武将（`BATTLE_MAX_ATTACKERS`），即最多 2 支满编队伍 + 1 支残编；
守方按兵多者取前 8 将各自成队（`BATTLE_MAX_DEFENDERS`）。

### 0. 结论先行

**当前地图的核心问题不是"某座关没调好"，而是三件事同时缺失：**

1. **没有区域骨架**：山脉是散落的"香肠"，不是连续的山墙；河流是"可以绕过源头的长水带"，不是分割线。全图仍然是一个大连通块。
2. **关不是门，渡不是门**：关隘只是路边的 1–3 格牌子，线外可以绕；渡口只是局部捷径，河流本身没有成为墙。
3. **仪表盘是坏的**：`weak` 把自家通行线算进绕行，12 座关 + 3 条小路全部误报"弱"；`_audit-map` 把水面当成陆地，所以"59 城全连通 / 武都孤岛"的结论都不成立；`stats` 读的是凿谷前快照；`cityBlocks` 在凿谷前已缓存，凿谷后武都中心变成山岭而无人发现。

**修法不是继续调 `RIDGES` 半宽，而是换一层地形模型：**

| 层 | 做法 | 解决什么 |
| --- | --- | --- |
| L0 地理底图 | 保留经纬度投影、海岸线、河流折线、山脉折线、城池坐标 | 地图仍然像中国 |
| L1 战略墙 | **关墙**：每座关/小路在道路上生成一道 1 格厚的横向山墙，两端接到最近的山体/水面；中间只留 1 格门洞。**河源封口**：每条大河的源头接进山体或海域 | 关成为唯一通路；河成为墙 |
| L2 门 | 关门 = 门洞；渡口 = 河墙上的摆渡跳跃边；新增缺口渡口 | 关港成为路网节点 |

**一句话：不再追求"把山加宽到堵住缺口"，而是"在每座关的位置造一道墙，墙上开一扇门"。**

### 1. 现状体检（2026-10-30 实测）

#### 1.1 先修尺子：三处仪表盘失真

| # | 位置 | 问题 | 后果 |

### 4. 方案：三层地形模型

#### 4.1 管线

```
L0 地理底图
  RIDGES / RIVERS / LAKES / CITY_COORDS
        ↓
L1 战略墙
  ① 关墙：每座 pass/trail 在道路上生成 1 格厚横向山墙 + 1 格门洞
  ② 河源封口：每条大河的源头接进山体/海域
        ↓
城池落位（3×3，避山/水；生成后不再被地形改写）
        ↓
L2 门
  ③ 关门：门洞 = center；lane = 门洞 + 两侧道路格
  ④ 渡口：渡线 + 两岸滩头 + 摆渡跳跃边
        ↓
校验：关墙/渡口/区域/绕行/存档
```

**关键顺序**：先造墙，再落城，再开门。当前顺序是"先落城（被缓存）→ 再凿谷 → 城池被改坏"，必须反过来。

#### 4.2 关墙生成算法（核心）

对每座 `pass` / `trail`：

1. 取 `edges[0]` 的两座城锚点 `A、B`；**以 `gate.anchor` 作为门洞 `P`**（不再投影到 `A–B` 直线）。
   - 没有 `anchor` → **失败**（不允许再取"道路中点"碰运气）。
   - 校验 `A→P→B` 折线长度 ≤ 1.8× 直线 `A–B`；超过说明锚点偏离道路，**失败**并要求改锚点（R5 另限 ≤2.5×）。
   - `P` 必须是山地 / 丘陵（或紧邻山体）；否则失败。
2. 道路方向取 `P` 处折线的角平分方向；横向 `perp = (-dir.y, dir.x)`。
3. 从 `P` 沿 `perp` 向两侧各走 1..24 格，找**最近的不可通行地形**（`mountain` / `river` / `lake` / `sea` / 地图边缘）作为墙端。
   - 只遇到 `hill` / `plain` / `forest` 不算墙端；走满 24 格仍未遇到 → **失败**，要求补山/补河或移锚点。
   - 墙端是水面时，墙停在紧邻水面的最后一格陆地；水面本身不改，靠"水面不可通行"闭合。
   - 墙端不得落在任何城池的 3×3、4 个门外格、或其他关港的 lane 上；若会压到 → **失败**。
4. **先凿路，再砌墙**：沿 `A → P → B` 把道路穿过的山体凿成 1 格宽、4 邻接的谷地（最多向两侧各延伸 12 格），写成 `hill`；
   然后在 `P` 与两个墙端之间画 4 邻接折线，全部写成 `mountain`；`P` 本身写成 `hill`（门洞）。
   - 谷地保证"门洞接得上路"；关墙保证"除了门洞，没有第二条路"。
5. 门洞两侧沿道路各取 1 格，组成 `lane = [前, 门, 后]`；`center = 门`；`approaches = [前前, 后后]`。
6. 封锁时封 `lane` 三格；因为墙是 1 格厚且 4 邻接连续，封门洞即断路。

**为什么不是"把山加宽"**：
- 武关缺口 15+ 格，加到能堵住就会切断地图（v1 的 P2 自己也承认）；
- 关墙只影响局部 5–24 格，不会改变整条山脉；
- 墙端接真实山/水，绕行必须绕过整座山/整条河，天然形成区域级绕行。

**为什么不是 ZOC**：
- 关墙落地后，R1 可达标；ZOC 会封掉 approach / 唯一陆门 / 卡死已进圈部队（v1 §9.1 已列）。
- **本轮不做 ZOC**。

#### 4.5 关港作为"1 格小城"

| 项 | 规则 |
| --- | --- |
| 占地 | 1 格（门洞 / 渡口图标），不占 3×3，不生成四门 |
| 墙 | 关墙由地形（山）构成，关门是墙上唯一的门洞 |
| 归属 | 沿用 `guardCityId` + `GateRuntime.ownerId` |
| 驻军 | 沿用 `garrisonGateId`，不占地图格 |
| 产出 | 沿用月度解送；新港取 tier3 下限 |
| 耐久 | 沿用 `fortification`；攻关 = 打这座 1 格小城 |
| 水军 | 港口是水军节点；敌对港口封锁渡口跳跃边（本轮不做水面 ZOC） |

**不新增 3×3 关城**：3×3 会让关墙出现 9 格缺口，反而破坏"唯一门"。

### 7. 风险与回退

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 关墙像"人工墙" | 视觉可信度 | 墙只 1 格厚、端点接真实山/水、只做 17 处；截图 QA |
| 关墙压城 / 封住唯一陆门 | 城池不可出 | 生成前检查 3×3 + 4 门外格 + 关港 lane；压到即 fail-fast |
| 关墙截断其他路 | 路网断裂 | 每墙生成后跑 `audit-map` 连通；墙长 ≤24；必要时加第二个门 |
| 河源封口后区域断粮 | AI 卡死 | 每区域 ≥2 出口（南中/辽东除外）；P3 AI soak |
| 45 关港太多 | 经济/AI/UI 膨胀 | 新港 tier3 下限；`GATE_COUNT` 常量；`sim:economy` 对比 |
| 测试硬编码 31 | 红 | 全部改 `GATES.length` / `GATE_COUNT` |
| 旧档部队卡在山里 | 读档坏档 | `TERRAIN_VERSION` + 读档吸附；`save.migrate.spec` |
| 性能退化 | 冷启动变慢 | 关墙只生成一次；`perf:check` ≤1.5× |
| 区域过度分割 | 战役节奏碎 | 区域 ≤14；每区 ≥2 出口（南中/辽东除外） |
| 回退 | 难以单阶段回滚 | 每阶段一个 commit；`gateWall.ts` 可单独停用，退回"凿谷" |

**回退策略**：P1 的关墙是新增模块，若失败可 `gateWall.enabled = false` 退回旧 `carveCorridors`；数据段（锚点/新增关港）单独 commit，可单独 revert。

#### 10.3 残余风险（实施中验证）

1. **关墙的视觉可信度**只能靠截图人工确认；程序填充的山墙可能比手绘山脉更"硬"。

5. **关墙与真实地理的偏差**：虎牢/函谷/嵩山北延是游戏化夸张，截图与文档要明确说明"可玩性优先"。

## 篇三 · 关隘诊断：为什么 8 座关在地理上不存在

> 这是篇二改造的**证据链**。结论很刺人：12 座关隘中 8 座封锁后绕行代价为 0 —— 不是位置没调好，是地形模型与「关隘」这个概念结构性错配。

---

> 起因：武关在地图上"毫无意义"——不可攻击、旁边空地能直接走。
> 本文回答的是**这一类问题**，不只是武关。

### 一句话结论

31 处关港里，**封锁后能让两端城池多绕 60 MP 以上的只有 3 处**（寻阳渡、白帝渡、子午谷）。
12 座关隘中，**8 座封锁后绕行代价为 0** —— 也就是说，它们在地理上根本不存在。

这不是"某座关的位置没调好"，而是地形生成模型与"关隘"这个玩法概念的结构性错配。

### 体检口径

只看一条：**封锁这座关之后，它两端城池之间的最短行军距离变长了多少。**

变长很多 → 这座关卡住了路，值得打。
几乎不变 → 敌人从旁边就走了，这座关只是一块插在山坡上的牌子。

工具：`npm run map:diag`（单座 `npm run map:diag -- <gateId>`，`-- --all` 输出全部轨迹）。
地形剖面、最短路轨迹、封锁前后对比都在里面。

### 数据

单位 MP（每旬移动力预算内的"进入一格扣多少"）。"无小路"一档把子午谷/轘辕道/阴平道一起封掉，
用来看"去掉奇袭路线后正关还剩多少价值"。

成对港口（赤壁/乌林、瓜洲/京口、采石/横江…）单封一处仍可走对岸那座，所以单关口径天然是 0，
这是设计而非缺陷。真正要看的指标是**整对一起封**：

- 寻阳渡 +80、白帝渡 +127 —— 有效。
- 其余单封 +0~+13，需按"成对封锁"重新体检（未做）。

- 轘辕道 +0、阴平道 +0 —— 名存实亡。

### 武关的尸检

三条独立的原因叠在一起，缺一条它都不会这么废。

#### 1. 地形：秦岭东端与伏牛山西端之间有一道 13 格的缺口，武关正落在缺口里

`RIDGES` 里秦岭的折线终点是 `(111.0, 33.55)`，伏牛山的起点原本是 `(111.6, 33.7)`。
两者之间空 0.6° 经度 ≈ 13 格。武关 `(111.02, 33.72)` 就在这个缺口中央。

地形剖面（`W` = 武关，`*` = 通行线，`M` = 山岭，`h` = 丘陵，`.` = 平原）：

```
 170 MMMMMMMMMMMMMMMMMMMMMMMMMM*MMMMMMMMMhhhhhhhhhhhhhhhhh
 171 MMMMMMMMMMMMMMMMMMMMMMMMMM*MMMMMMMMMMMMMMMMMhhhhhhhhh
 172 MMMMMMMMMMMMMMMMMMMMMMMMMMWMMMMMMMMMMMMMMMMMMMMMMMhhh   ← 武关东侧全是可走的丘陵
 173 MMMMMMMMMMMMMMMMMMMMMMMMMM*MMMMMMMMMMMMMMMMMMMMMMMMMM
 174 MMMMMMMMMMMMMMMMMMMMMMMMMM*MMMMMMMMMMMMMMMMMMMMMMMMMM
```

西边是秦岭主体（不可通行），东边从 272 列起就是丘陵 —— 2 MP/格，能走。
所以"旁边的空地"是真的空地。

#### 2. 落位：那条 21 格的通行线是沿着山脊纵向走的，不是横穿山体

`buildPassSite` 挑的是"离道路中点最近的山脊"，而秦岭在这一带是东西向的，
最近的可用山脊正好是它的**东缘**——于是通行线顺着边缘南北走 21 格。
从这条线的北口绕到南口只要 58 步，和走线本身（21 步）差不多。

试过把落位判据改成"挑山体最薄处 + 线外绕不过去"：武关的通行线缩到 14 格，
但潼关的绕行惩罚从 +17 掉到 +0 —— 因为它被推到了离道路 10 格外的薄口上，
路根本不经过那里。**挪关卡救不了地形**，已回退。

#### 3. 数值：子午谷比走武关道更快

长安→宛的最短路轨迹（116 步，123 MP）**经过的是子午谷，不是武关**。
子午谷 33 格通行线 +6 日 = 39 MP 就穿过了秦岭，然后沿汉水谷地东行到宛。
而武关道要沿渭河平原东行 48 格（其中一段是丘陵，2 MP/格）再南下。

把子午谷的 `extraDays` 从 6 提到 25 时，路径确实改走武关了 —— 但封锁武关后总距离仍是 134，
因为绕回去走子午谷也是 134。**两条路等价，武关没有优势。**

### 根因（三层的共同点）

地图是"山脉折线 + 半径"程序生成的，而三国志11 的地图是手绘的：

| | 三国志11 | 本项目 |
|---|---|---|
| 山 | 画成连续的墙 | 折线 + 半宽，M 区实际只有 5–10 格宽 |
| 关隘 | 画在墙上唯一的缺口 | 落在"离道路中点最近的山脊"上 |
| 道路 | 画在山谷里 | 由地形代价决定，常常沿着山走而不是穿山 |
| 绕行 | 画不出来 | 折线之间到处是缺口 |

所以问题不是"武关没调好"，是**没有任何机制保证"关隘所在处是唯一通路"**。

### 试过并失败的方案（负面结果，省得再走一遍）

#### ✗ 挪关卡：挑"山体最薄处"

把 `buildPassSite` 的评分从"离道路中点最近"改成"山道最短"，并把"线外绕不过去"作为硬判据。

结果：武关的通行线从 21 格缩到 14 格（确实更薄了），但**潼关的绕行惩罚从 +17 掉到 +0** ——
它被推到了离道路 10 格外的薄口上，路根本不从那里走。关隘"薄"但"不在路上"，比原来更没用。

结论：**挪关卡救不了地形。** 已回退，`isWeakPass` 只保留为诊断标记。

#### ✗ 补山：把通行线两侧填成山

沿通行线向两侧延伸补山，遇到已有山体/水面/城墙/其他通行线就停。

- 不设上限（40 格）→ **把地图切断了**：潼关、武关、散关在"无小路"口径下距离变成 ∞。
  补山墙横穿了几条本来能走的走廊。
- 设上限（6 格）→ 绕行缺口还在，封锁后仍然 +0。

结论：武关所在的缺口有 20+ 格宽（东西）× 21 格（南北），
补到能堵住缺口的宽度就会切断地图，补到不切断地图的宽度就堵不住。**局部补山无解。**

#### ✗ 调数值：把子午谷代价从 6 提到 25

路径确实改走武关了（`经过武关=true`），但**封锁武关后总距离仍是 134** ——
因为绕回去走子午谷也是 134。两条路等价，武关没有优势。

结论：数值只能改变"走哪条路"，改变不了"能不能绕"。武关道的几何本身就不比子午谷短。

#### ✓ 有效但不够：伏牛山西端与秦岭咬合

`(111.6, 33.7)` → `(110.85, 33.78)`，宽度 0.32 → 0.42。武关东侧不再是一望无际的丘陵，
但缺口仍有 15 格以上，绕行照旧。**这是必要的修正，但不是充分的。**

### 所以真正的修法只有一条

**重画关隘所在处的地形**，让它成为"两侧是墙"的通道。两条路线：

#### A. 凿山谷（推荐，最接近三国志11）

为每条挂了关隘的道路凿一条 1 格宽谷地，从 A 城附近穿到 B 城附近，关隘卡在谷中最窄处。

- 改动：`terrainGrid` 增加 corridor 逻辑（把山体格改成丘陵，可通行），corridor 数据从 `GATES.edges` 推导。
- 效果：长安→宛变成"必须走武关道"，封锁即断路。
- 风险：全图会出现 12 条人工山谷，战略格局会变（原本绕不过去的地方变得能过）。
- 这是唯一能同时满足"关卡有意义"和"地图不被切断"的做法 —— 因为它同时做两件事：
  凿出唯一通路 + 通路两侧保持山体。

#### B. 重新设计关隘机制（不改地形）

承认地形无法保证"必经"，把关隘从"闸门"改成"控制点"：

- 关隘不封锁通行线，而是对**经过其控制范围（半径 R）的敌军**施加惩罚：
  伏击减员 / 额外行军消耗 / 视野暴露。
- R 由 `tier` 决定，覆盖整条缺口。
- 好处：不需要动地形，弱关也有意义（拦住不划算，但过路要付代价）。
- 代价：偏离三国志11 的手感，是另一套玩法。

### 已经落地的改动

1. `RIDGES` 伏牛山西端与秦岭咬合（真实地理修正，见上）。
2. `GateSite.weak` 标记 + `map:gates` 输出：线外可绕的关隘会明确标出来
   （当前 9 处：潼关、函谷关、虎牢关、剑阁、葭萌关、祁山堡、瓦口关、轘辕道、阴平道）。
3. `scripts/diag-gates.ts`（`npm run map:diag`）：可复现的有效性诊断（地形剖面 + 封锁前后对比 + 最短路轨迹）。
4. `gateSites` 拆出 `computeSites`，为将来"整形地形后重算落位"留出入口。

### 未决

- 港口需要按"成对封锁"重新体检，本轮只做了单关口径。
- `weak` 用的是局部绕行 BFS，和全局最短路口径有出入（武关就被漏判了）。
  正式落地时应改成"封锁前后全图距离差"。
- 12 座关隘里只有壶关（+27）、潼关（+17）勉强算"有点用"，
  其余 10 座在凿谷方案落地前都只是地图装饰。

## 篇四 · 技术选型：要不要换引擎

> 这是全卷唯一的**否定性结论**：五个目标能力里有四个与引擎无关，换引擎买不到「三国志11 的观感」。末尾附 P0 落地记录。

---

> 评估对象：《三国霸业》全地图表现层（576×432 格）能否通过引入第三方引擎或工具，达到《三国志11》式的地图观感与交互。
> 基线：2026-10-29 工作区（`src` 38,654 行 / 113 文件；`render` 7,357 行；`ui` 7,228 行；`tests` 7,770 行 / 45 文件）。
> 性质：只做选型评估与路线设计，不含实现。
> 结论口径：**能，但收益不在引擎。** 目标拆成 5 项能力后有 4 项与引擎无关；换引擎真正买到的是地形质感与交互手感，代价是重写 2,000–3,000 行渲染层。

---

### 0. 结论先行

1. **最大缺口是缺一层数据，不是缺渲染能力。** 全项目没有"每格归属"概念（`territory` / `influence` / `版图` 在 `src` 下零命中），势力色只以城池同心光晕表达。三国志11 最标志性的"版图铺色 + 墨迹边界"，任何引擎都不会自动给你。
2. **第二缺口是地图层没有渲染循环。** `MapCanvas` 全文无 `requestAnimationFrame`、无 ticker，全部由 React 状态变化触发全量重绘。行军箭头流动、部队位移插值、季节色调过渡这类"活的地理"，缺的是循环，不是 GPU。**注意 `BattleCanvas` 已有现成范式**（`fxCanvasRef` 独立特效层 + rAF + 30fps 节流 + `prefers-reduced-motion`），地图层只是没照搬——这让 P0-2 从"新架构"降级为"内部复制一个已验证的写法"。
3. **第三缺口是交互数学。** 滚轮缩放锚定"选中城池/屏幕中心"而非鼠标位置；无惯性；移动端无双指捏合；`imageSmoothingEnabled = true` 与"新国风像素"方向直接冲突。这三项合计约 150–250 行，不需要任何引擎。
4. **Web 端值得引入的只有一个：PixiJS 8（MIT，8.22.0 / 2026-10-01）。** 它只替换绘制内核，不动状态层与 React UI；纯几何模块可原样复用；可回退。
5. **Phaser 4（MIT，4.2.1 / 2026-07-09）技术上有更优的瓦片管线**——`TilemapGPULayer` 把整张瓦片图作为单个 quad 渲染，成本按屏幕像素计而非瓦片数——但它把输入、相机、场景一并接管，与本项目「纯函数 reducer + React UI」的职责划分重叠。**只在 PixiJS 路线被证伪后再议。**
6. **Godot / Unity / Cocos / LayaAir 全部否决。** 等于重写 38,654 行逻辑 + 7,228 行 UI + 396 项测试，并放弃 Web 首屏。这不是换引擎，是换项目。
7. **最高性价比的"工具"是 Tiled。** 项目现在靠 `scripts/gen-map.ts` 程序化生成 + ASCII 预览维护 24.9 万格，缺的是可视化编辑器。这一项的收益大于任何引擎。

### 2. 目标拆解：5 项能力该归因给谁

这是本评估最重要的一张表。**先把"缺什么"归对类，再谈买什么。**

| # | 能力 | 现状 | 真正缺的东西 | 归因 | 引引擎的边际收益 |
| --- | --- | --- | --- | --- | --- |
| ① | 城池与关隘布局 | 已有 3×3 城郭 + 四门 + 47 关防，代码绘制 | 像素资产、部件组合、缩放级 LOD | **资产** | 中（atlas / LOD / 滤镜） |
| ② | 势力版图着色 | **完全没有**，只有城池光晕 | `tileOwner` 数据 + 场计算 + 边界提取 | **数据 + 算法** | ≈0 |
| ③ | 地形与通行可视化 | `paintTerrain` 程序化绘制，18 px/格烘焙 | tileset 或 shader、山脉河流剪影 | **表现 + 资产** | 中高 |
| ④ | 行军路线可视化 | 有静态 reach / preview 高亮，无动画 | rAF 循环 + 路径动画 + 箭头精灵 | **表现（循环）** | 中 |
| ⑤ | 缩放拖拽点击 | 有基础缩放 / 拖拽 / 拾取 | 锚点、惯性、捏合、整数吸附 | **交互数学** | 高 |

**读法**：②是最大单项收益、且引擎贡献为零；⑤引擎贡献最高，但成本是 150 行数学；③是唯一"引擎明显更好"的一项。所以——

> 换引擎的最佳理由只有一条：**要把地形从"每帧程序化画"改成"GPU 瓦片/shader"，顺带拿到滤镜级质感。**
> 如果目标只是"版图铺色 + 路线会动 + 缩放跟手"，换引擎是负收益。

### 6. 推荐优先级

#### P0 · 先补地基（不换引擎，1.5–2.5 周）

| 编号 | 事项 | 做法 | 行数 | 为什么先做 |
| --- | --- | --- | --- | --- |
| **P0-0** | 补渲染基准 | 新增 `scripts/render-bench` 或在 dev 页加 FPS/帧时间 HUD；记录 20% / 100% / 720% 三档、桌面与中端手机各一组 | ~120 | 没有基准就没有选型依据；`perf:check` 明文不测 FPS |
| **P0-1** | 势力版图 | `tileOwner: Uint8Array(576×432)`；每月以城池为源、按地形代价做**多源 Dijkstra 场**（248k 格，预期 < 20ms）；`d3-contour` 提边界；Canvas 填充 + 内描边 + 外模糊 | ~350 | **三国志11 感的最大单项来源**，且与引擎无关 |
| **P0-2** | 渲染循环 + 分层 | 照搬 `BattleCanvas` 的 fx 层写法：静态层（地形/版图/道路）烘到离屏 canvas，脏标记失效；动态层（部队/高亮/标签）独立 canvas + rAF + 节流 + reduced-motion | ~250 | 解决 hover 全量重绘；为 ④ 动画提供载体；范式已在仓库内验证，不是新技术风险 |
| **P0-3** | 相机手感 | 光标锚点缩放、惯性衰减、双指捏合、缩放档位吸附到整数倍（像素美术必需）、`imageSmoothingEnabled=false` | ~200 | 四项合计成本最低、感知最强 |
| **P0-4** | 资产管线 | Tiled 出地形图块与城池部件 → 图集（free-tex-packer / TexturePacker）→ 运行时 blit；确立"程序化生成 vs 手工编辑"的权威源 | ~300 + 资产 | ①③ 的前置；没有资产，引擎再好也画不出地标剪影 |

**P0 完成后的预期状态**：版图会铺色、道路会流动、缩放跟手、地形是像素图块——**目标里的 4 项已达成，且没引入任何新依赖。**

#### P1 · 换内核（3–5 周，有条件触发）

引入 **PixiJS 8**，只替换 `src/render` 的绘制内核。

**触发条件（满足任一）**：
- P0-1 完成后，中端手机在 100% 缩放下 P95 帧时间 > 20ms；
- 需要 shader 级质感：墨迹晕染边界、宣纸纹理叠加、季节色 LUT、水面波动、雨雾；
- 需要 60fps 持续动画（部队行军逐格位移、旗帜飘动）。

**止损点**：若 2 周内 `MapCanvas` 主路径未跑通，退回 R0 并把 shader 效果降级为静态贴图。

Phaser 4 + `TilemapGPULayer`。前提是 P0-4 已完成地形 tileset 化——**否则瓦片管线无从发挥**。

### 8. 三个待裁决问题

1. **像素整数缩放 vs 连续缩放。** 美术方向是"新国风像素、32×32 单位"，那么缩放应吸附到整数倍（1×/2×/3×…）以免糊边；但整数档位会让"从全图到城池特写"的过渡变跳。**建议**：渲染用整数倍，UI 上做 150ms 的 cross-fade 掩盖跳变。
2. **版图语义。** 三种可选：①城辖领内（城市周围固定半径，最像三国志11，但山区会溢出）；②道路可达（沿驿道扩张，最合理，但算法与关隘封锁耦合）；③影响力场（距离衰减 + 兵力权重，最好看，最难解释给玩家）。**建议**先做 ②，因为它与已有 `gates` 通行线天然一致。
3. **是否接受两套渲染栈的过渡期。** R1 期间 `MapCanvas`（Pixi）与 `BattleCanvas`（Canvas 2D）会并存 1–2 个版本。可接受，但要在 `docs` 里明确标注废弃时间点，否则半年后没人敢删旧代码。

#### 9.2 帧耗时：优化前 → 优化后

同一台机器、同一份负载（1280×800，DPR 2，无头 Chrome）：

| 阶段 | 优化前 P95 | 优化后 P95 | 优化前 max | 优化后 max |
| --- | --- | --- | --- | --- |
| hover 扫图 @100% | 16.8 ms | 16.7 ms | 50.0 ms | 16.8 ms |
| 滚轮缩放 ×60 | 49.9 ms | 16.8 ms | 50.1 ms | 16.8 ms |
| 全图 ↔ 近景 ×60 | **150.0 ms** | **16.7 ms** | **266.6 ms** | 16.8 ms |

**结论**：真正的问题不是"每帧重绘太慢"，而是**缩放时同步现烘地形**——一次缩放要几十块，
LRU 32 块装不下，于是出现 150–266ms 的长帧。改成"先垫底、后补烘"后，三档全部锁在 60fps。
`createRadialGradient` 的优化是次要收益，但它让 hover 的最差帧从 50ms 降到 16.8ms。

> **这个仪器测的是"掉帧"，不是"余量"。** rAF 间隔恒为 16.7ms 意味着没有掉帧，
> 不代表每帧只花 5ms。想知道离掉帧还有多远，得在 paint 函数里打点（下一步再做）。
> 反过来说：**P0-0 的基准推翻了本文档 §1.1 的假设 1**（"hover 全量重绘是主要瓶颈"）。
> 这正是先量再改的价值——如果不测，很可能会去做一个收益不存在的静态/动态分层重构。

#### 9.4 P0-4 为什么没做

资产管线的前提是"有人画图块"。当前项目是**零素材**路线（地形 1,728 行程序化绘制、音效全部合成），
引入 Tiled + 图集等于同时引入一条美术生产链，这不是代码工作量的问题，是**由谁出图、出多少张**的产品决策。

在决策落地前先搭 loader 只会得到一堆死代码，所以这一项留空。
建议顺序：先定"程序化地形是否保留" → 若保留，P0-4 降级为"只给城池 / 关隘做部件图集"；若不保留，再整体转 tileset。

#### 9.5 仍未收敛的参数

- **染色强度**：`territoryWash()` 现在 20% → 0.87、100% → 0.55、≥200% → 线性降到 0.15。
  100% 这一档偏"灰紫"，需要对着实际显示器再调一次（无头截图有色彩偏差）。
- **墨线宽度**：现在靠 1 px/格 边缘 + `blur(1.1px)`，全图看是软边，近景看略糊。若 P1 上 shader，可改成按屏幕导数取宽。
